# Mosaic Protocol 0.3

## Status and authority

Protocol `0.3` is a **release candidate**, not an approved contract. It is
coherent, implementable, and fully validated, but it is **not immutable**: the
[cross-platform implementability gate](release-approval-process.md#cross-platform-implementability)
cannot have passed, because the Flutter, SwiftUI, and Jetpack Compose renderers
for `tabs`, `timeline`, `award`, and `socialProof` are being written now and
Studio cannot yet author them.

Release-candidate status is also the practically correct state for this work:
renderer implementation is exactly where a schema problem surfaces, and a
candidate can still absorb a narrowing correction under the
[narrowing doctrine](breaking-change-process.md#the-narrowing-pre-approval-doctrine).
An approved contract cannot.

Local Preview `0.3` is a release candidate for the same reason: it is
version-locked to this contract and cannot be approved while the contract it
carries is a candidate.

### What must pass before 0.3 can be marked approved

The full checklist is
[the approval checklist](release-approval-process.md#approval-checklist). The
items that are **specifically outstanding for `0.3`**, as opposed to already
satisfied by the carried-forward `0.2` surface, are:

1. **`tabs`, `timeline`, `award`, and `socialProof` are implemented — or carry
   an explicit declared fallback — in the Flutter, SwiftUI, and Jetpack Compose
   renderers.** Rendering "the closest thing" without a declared fallback does
   not count.
2. **Tab selection is implemented as runtime state on all three renderers**,
   including reset on an accepted revision, and `visibility.mode: "tab"`
   removes a node from layout, the accessibility tree, and focus order rather
   than merely hiding it visually.
3. **tablist/tab/tabpanel semantics are verified on each platform** with its
   native accessibility APIs, along with the Timeline ordered-list, Award group,
   and Social Proof group announcements and their decorative markers, emblems,
   and avatars.
4. **Studio authors and validates every new component**, including the
   required `initialTabId` and `selectedLabelColor`, the Timeline
   marker/description co-presence rules, and the integer rating scale.
5. **The backend produces, validates, and negotiates `0.3`**, and its vendored
   schema copy is re-synced. Schema, semantic validator, and API runtime
   validation must agree; disagreement among the three is a release blocker.
6. **Capability negotiation delivers `0.3` only to readers declaring exact
   support** for all five new capabilities.
7. **Every `0.2` reference outside `protocol/` is purged** — the SDKs, Studio,
   backend, and examples still carry `0.2` constants, `V02` symbols, and
   `fixtures/v0.2/` paths.
8. **Protocol-owner, quality, product, and UX reviews recorded, and
   product-owner approval recorded.** `0.3` adds four authored, rendered
   components, so the UX review is required rather than optional.
9. **Any narrowing correction the renderer work surfaces is applied before the
   flip**, with fixture evidence. This is the last state in which that is
   permitted.

Once approved, `0.3` behaviour and fixtures are frozen and a behaviour change
requires a new Paywall Protocol version — see the
[breaking-change process](breaking-change-process.md) and the
[deprecation policy](deprecation-policy.md).

`0.3` **replaces `0.2` outright.** It is not a successor that `0.2` documents can
be upgraded into: a `0.2` document is rejected by the `0.3` reader like any other
unknown version, there is no migration path, no migration tool, and no
compatibility shim. Every `0.2` artifact — schema, compatibility manifest,
fixtures, Local Preview schema and fixtures, and the `V02` reference
implementation symbols — has been deleted from the tree rather than deprecated
alongside `0.3`. Mosaic is pre-release; carrying a second paywall contract would
cost more than it protects. This is a recorded owner decision, not an
engineering inference.

`protocol/compatibility/v0.3.json` records
`status: "releaseCandidate"` with `releaseCandidate: "RC1"`. The lineage record
restarts at RC1 because `0.3` replaces `0.2` rather than succeeding it.
Pre-release Protocol and Local Preview `0.1`, and Protocol `0.2`, are retired
and deleted; `0.3` is the only Paywall contract in the tree.

Canonical artifacts:

- `protocol/schema/v0.3/paywall.schema.json`
- `protocol/compatibility/v0.3.json`
- `protocol/fixtures/v0.3/complete-paywall.json`
- `protocol/fixtures/v0.3/edge-cases.json`
- `protocol/fixtures/v0.3/rating-announcement.json`
- `protocol/fixtures/v0.3/accessibility-announcement.json`
- `protocol/fixtures/v0.3/invalid/`

The document is closed and declarative. Unknown properties, missing or cyclic
references, unsafe URLs, executable content, and arbitrary expressions reject
the complete document atomically.

## Document design system

Every document contains three bounded catalogs. Empty catalogs are valid; each
catalog accepts at most 256 entries.

```json
{
  "designSystem": {
    "colors": [
      { "id": "brand-primary", "name": "Brand primary", "value": "#007F73FF" },
      {
        "id": "brand-accent",
        "name": "Brand accent",
        "value": { "type": "colorToken", "id": "brand-primary" }
      }
    ],
    "backgrounds": [],
    "shadows": []
  }
}
```

Token IDs and display names are unique inside their category. Colour,
background, and shadow references resolve only inside their own category.
Token-to-token references are allowed, but every reference must resolve and
the graph must be acyclic. Renderers resolve tokens from the accepted document;
there is no server or project design-library lookup at render time. Editing an
inline value after choosing a token is an authoring concern: Studio detaches
the field from the token instead of mutating the token silently.

## Colours, backgrounds, and shadows

A `Color` is one of the existing semantic names, canonical uppercase
`#RRGGBBAA`, or a strict token reference:

```json
{ "type": "colorToken", "id": "brand-primary" }
```

A `Background` is exactly one of:

```json
{ "type": "color", "value": "surface.default" }
```

```json
{
  "type": "linearGradient",
  "angle": 135,
  "stops": [
    { "position": 0, "color": "surface.default" },
    { "position": 1, "color": { "type": "colorToken", "id": "brand-primary" } }
  ]
}
```

```json
{
  "type": "radialGradient",
  "center": { "x": 0.5, "y": 0.25 },
  "radius": 1,
  "stops": [
    { "position": 0, "color": "surface.elevated" },
    { "position": 1, "color": "transparent" }
  ]
}
```

```json
{
  "type": "image",
  "assetId": "offer-texture",
  "contentMode": "fill",
  "fallbackColor": "surface.default"
}
```

```json
{
  "type": "video",
  "assetId": "offer-video",
  "posterAssetId": "offer-poster",
  "contentMode": "fill",
  "fallbackColor": "surface.default"
}
```

```json
{ "type": "backgroundToken", "id": "offer-gradient" }
```

Gradients contain two through eight stops. Positions are in `0...1`, strictly
increasing, and unique. Linear angle is a physical canvas direction from the
first stop to the last: `0°` is left-to-right, `90°` is top-to-bottom, angles
increase clockwise, and RTL never mirrors the angle. The accepted range is
`0...360`, where `360°` is equivalent to `0°`. Radial center coordinates
are normalized `0...1`; radius is positive and at most `2`.

Media backgrounds are decorative: they never expose accessibility content or
controls. Video is always muted, autoplaying, looping, and control-free. When
video cannot load, the renderer uses its declared poster if that image is
available, then the declared fallback colour. An unavailable image uses its
fallback colour. Every failure emits a safe diagnostic and never crashes the
host.

Eligible authored boxes accept one shadow:

```json
{
  "type": "shadow",
  "color": "#00000033",
  "offsetX": 0,
  "offsetY": 8,
  "blurRadius": 24
}
```

or `{ "type": "shadowToken", "id": "floating" }`. `0.3` has no spread,
blend mode, backdrop blur, multiple shadows, or ordered effect stack. Product
Card, Product Badge, and Tabs Default/Selected box styles use this same shadow
model.

## Assets

Image and video assets use a bundled logical key or a safe absolute HTTPS URL:

```json
{
  "type": "image",
  "id": "offer-poster",
  "source": { "type": "remote", "url": "https://assets.example.com/poster.webp" },
  "fallback": {
    "type": "placeholder",
    "value": {
      "default": "Image unavailable",
      "localizationKey": "paywall.assets.poster_fallback"
    }
  }
}
```

```json
{
  "type": "video",
  "id": "offer-video",
  "source": { "type": "bundled", "key": "mosaic.offer.video" }
}
```

Remote URLs must be absolute HTTPS, at most 2,048 characters, and contain no
credentials, control characters, malformed hosts, or invalid ports. An Image
component references only an image asset. Image/video backgrounds and poster
references must match their declared asset type.

## Uniform sizing

Every eligible authored box uses one optional uniform sizing object:

```json
{
  "sizing": {
    "width": "fill",
    "height": { "mode": "fixed", "value": 180 }
  }
}
```

Both axes are required when `sizing` is present. Each axis is `"fit"`,
`"fill"`, or `{ "mode": "fixed", "value": positiveLogicalSize }`.
Candidate value `"content"` is replaced by `"fit"`.

Stack, Text, Image, Icon, Feature List, Product Selector, Product Card,
Product Badge, Button, Carousel, Switch, Countdown, Tabs, Timeline, Award, and
Social Proof are eligible. Screen
Scroll Container is viewport-owned and excluded. Image may retain an optional
positive `aspectRatio` as intrinsic-ratio guidance; it has no separate width or
height field.

Fixed boxes clip visual overflow while the full semantic value remains
available to assistive technology. Fill requires a bounded parent axis. If the
axis is unbounded, the renderer uses Fit and emits `layout.unboundedFill`
instead of failing or producing infinite layout.

## Screen and Sheet presentation

Every screen declares presentation explicitly:

```json
{ "presentation": { "type": "screen" } }
```

or:

```json
{ "presentation": { "type": "sheet" } }
```

`initialScreenId` must reference a Screen. A Sheet presents on the native modal
surface over the most recent Screen in navigation history, remains within the
safe viewport, and scrolls internally through its existing Scroll Container.
`navigateBack` dismisses/pops it through the same history model. Converting a
Screen to Sheet or Sheet to Screen changes only `presentation`; ID, content,
actions, and references remain unchanged.

`0.3` has no detents, draggable sheet handle, nested presentation options,
custom transition, or arbitrary screen position. The existing rules remain:
one through ten screens, globally unique component IDs, complete reachability,
screen-local purchase/Switch references, and an acyclic `navigateTo` graph.

## Components, actions, and product structure

`0.3` carries forward every `0.2` component and action unchanged:

- generalized vertical/horizontal Stack;
- Text, Image, Icon, Feature List, Carousel, Switch, and Countdown;
- one composable Button with Purchase, Restore, Close, Navigate To, Navigate
  Back, or Open External URL;
- Product Selector with ordered authored Product Cards and optional Product
  Badge content;
- complete Default plus recursively partial Selected box styles; and
- closed `{{ product.name }}` / `{{ product.price }}` substitution inside
  Product Card content and accessibility copy only.

and adds four components — **Tabs**, **Timeline**, **Award**, and **Social
Proof** — specified below.

No remote executable behavior, arbitrary interpolation, or platform resource
identifier is part of the protocol.

## Tabs

Tabs presents N labelled panels with exactly one visible at a time. It is the
second component after Switch to own runtime selection state, and the first to
own state that is not Boolean.

```json
{
  "type": "tabs",
  "id": "billing-tabs",
  "tabBarDirection": "horizontal",
  "tabBarGap": 8,
  "tabBarDistribution": "spaceBetween",
  "gap": 16,
  "initialTabId": "billing-tabs-annual",
  "tabs": [
    {
      "id": "billing-tabs-monthly",
      "label": { "default": "Monthly", "localizationKey": "paywall.tabs.monthly_label" },
      "content": { "type": "stack", "id": "billing-tabs-monthly-content", "...": "..." }
    }
  ],
  "styles": { "default": { "...": "..." }, "selected": { "...": "..." } },
  "labelTypography": { "...": "..." },
  "selectedLabelColor": "action.onPrimary",
  "accessibility": { "label": { "default": "Compare billing periods", "localizationKey": "paywall.tabs.label" } }
}
```

Two through eight tabs. Each entry declares an `id`, a localized `label`, and a
`content` Stack. Tab IDs join the one global layout ID namespace, because a tab
ID names a control, a panel, and the value a visibility condition compares
against.

`initialTabId` is **required** and must name a declared tab. There is no
positional default: with a default of "the first tab", reordering the `tabs`
array would silently change which panel opens, and a reorder is a layout edit
that no author expects to change behaviour.

`selectedLabelColor` is **required**, not an optional override. A selected tab
that deliberately keeps its Default label colour and a selected tab whose colour
was never authored are different intentions that an absent field cannot tell
apart, so the author states the colour either way. Everything else about the
selected state is the same recursive Default-plus-partial-Selected overlay that
Product Card uses.

### Tab selection as a visibility condition

`visibility` gains a third conditional mode alongside `always`, `hidden`, and
`switch`:

```json
{ "mode": "tab", "tabsId": "billing-tabs", "equals": "billing-tabs-annual" }
```

The node is visible only while that Tabs component's runtime selection equals
that tab. As with Switch conditions, a false condition removes the node from
layout, the accessibility tree, and focus order — it does not merely hide it
visually. Four rules reject the document atomically:

1. `tabsId` must name a Tabs component declared **on the same screen**;
2. `equals` must name a tab **that component declares**;
3. the referencing node must not be the Tabs component itself; and
4. the referencing node must not be a **descendant** of that Tabs component.

Rule 4 is the one that has no Switch analogue. Inside a panel the condition is
already decided by the panel: comparing against the owning tab is vacuously
true, and comparing against any other tab is unsatisfiable. Both are dead
layout, and dead layout that renders is indistinguishable from working layout
until someone tries to edit it.

### Accessibility

The component carries one `accessibility.label` naming the tab list. Renderers
expose the component as a **tablist**, each tab control as a **tab** named by
its `label` and carrying its selected state, and each panel as a **tabpanel**
named by the same `label` and associated with its tab. There is no second
authored string for the panel: one label cannot drift from the other if there is
only one.

## Timeline

Timeline is an ordered sequence of steps — the "how your free trial works"
pattern of today, reminder, charge.

```json
{
  "type": "timeline",
  "id": "trial-timeline",
  "orientation": "vertical",
  "gap": 16,
  "connector": { "color": "border.default", "width": 2, "style": "solid" },
  "markerColor": "action.primary",
  "markerSize": 12,
  "entries": [
    {
      "id": "trial-today",
      "marker": { "kind": "dot" },
      "title": { "default": "Today", "localizationKey": "paywall.timeline.trial.today_title" },
      "description": { "default": "Full access starts immediately.", "localizationKey": "paywall.timeline.trial.today_description" }
    },
    {
      "id": "trial-charge",
      "marker": { "kind": "icon", "name": "lock" },
      "title": { "default": "Day 7", "localizationKey": "paywall.timeline.trial.charge_title" }
    }
  ],
  "titleTypography": { "...": "..." },
  "descriptionTypography": { "...": "..." },
  "accessibility": { "label": { "default": "How your free trial works", "localizationKey": "paywall.timeline.trial.label" } }
}
```

Two through twelve entries. Array order **is** the sequence order and carries
meaning; renderers must not reorder.

`orientation` is a required `"vertical"` constant, following the Scroll
Container `axis` precedent. Horizontal timelines are deferred rather than
approximated: they need different connector routing, different RTL mirroring,
and a different truncation model for long titles. Emitting a required constant
now reserves the axis without inventing a default that a future value would
silently change.

### Marker vocabulary

`marker` is a closed union with three arms — `{"kind":"dot"}`,
`{"kind":"ordinal"}` (the entry's 1-based position, formatted by the platform's
locale number formatting), and `{"kind":"icon","name":<iconName>}` drawing from
the existing shared icon vocabulary. An unrecognised `kind` rejects the
document; there is no substitute glyph.

### Absent values

- **`marker` absent** means the entry carries no glyph and the connector runs
  unbroken through its position. It is not a request for a default marker.
- **`description` absent** means the entry has a title and nothing else. The
  renderer draws no empty second line and reserves no space for one.
- **`markerColor`, `markerSize`, `descriptionTypography`** are each required
  when at least one entry consumes them and **forbidden** when none does. Both
  directions are enforced. Missing style where a marker exists would leave the
  renderer choosing a colour; declared style where no marker exists is a value
  nothing reads, which is how a stale field survives a redesign unnoticed.

### Connector geometry

> **Narrowing correction, 2026-08-06.** Terminal geometry was unspecified, which
> is visible pixel divergence across three platforms. Ruled below.

The connector occupies a dedicated leading gutter running the length of the
component. The gutter's cross-axis width is `markerSize` when any entry declares
a marker, and `connector.width` when none does. Markers and the connector are
both centred in that gutter.

The connector is **one continuous run**, drawn first; markers are drawn over it.
It therefore never breaks, and an opaque marker simply occludes the segment
behind it. This is what makes the existing rule — an absent marker leaves the
connector unbroken — fall out for free rather than being a special case:
connector geometry is identical whether an interior entry has a marker or not.
The only thing an absent interior marker changes is that nothing occludes the
run at that point.

The two ends are where the marker does change geometry:

- **Head.** If the **first** entry declares a marker, the connector begins at
  that marker's centre — there is no connector above it. If the first entry
  declares no marker, the connector begins at the top edge of that entry's
  content box.
- **Tail.** Symmetrically: if the **last** entry declares a marker, the
  connector ends at that marker's centre, with no connector below it. If it
  declares none, the connector ends at the bottom edge of that entry's content
  box.

Head and tail are decided independently — a timeline whose first entry has a
marker and whose last does not begins at a marker centre and ends at a content
edge.

"Top" and "bottom" are physical and never mirror: the timeline is vertical, so
an RTL catalog changes the gutter's side (leading, hence right) but not the
connector's direction of travel.

Renderers expose the component as a labelled ordered list, each entry as one
item announcing its title then its description, and treat markers and connectors
as decorative.

## Award

Award is a recognition or accolade — "App of the Day", "Editor's Choice". It is
passive: no action, no runtime state.

```json
{
  "type": "award",
  "id": "press-award",
  "direction": "vertical",
  "gap": 8,
  "crossAxisAlignment": "center",
  "emblem": { "type": "image", "assetId": "award-emblem", "size": 48 },
  "title": { "default": "Editor's Choice", "localizationKey": "paywall.award.press.title" },
  "titleTypography": { "...": "..." },
  "accessibility": { "label": { "default": "Press recognition", "localizationKey": "paywall.award.press.label" } }
}
```

`emblem` is a closed two-arm union over the **existing** asset and icon
vocabularies: `{"type":"image","assetId":…,"size":…}` referencing a declared
image asset, or `{"type":"icon","name":…,"size":…,"color":…}` drawing from the
shared icon names. An emblem image participates in the same asset-reference
rules as an Image component: it must resolve, it must be an image asset, and it
counts toward the "no unused asset" check.

**`emblem` absent** means the award renders its text alone. It is not a request
for a generic badge. **`subtitle` absent** means the award has a title and
nothing else; `subtitle` and `subtitleTypography` are mutually
`dependentRequired`, so neither can appear without the other.

The emblem is **always decorative** and there is no field to change that: the
`title` already carries the award's meaning, so an emblem alt-text would either
duplicate it or contradict it.

## Social Proof

Social Proof is a testimonial: an attributed quotation, optionally rated and
optionally illustrated. Passive: no action, no runtime state.

```json
{
  "type": "socialProof",
  "id": "rated-review",
  "gap": 8,
  "quote": { "default": "Mosaic replaced three internal tools.", "localizationKey": "paywall.social.rated.quote" },
  "quoteTypography": { "...": "..." },
  "attribution": { "default": "Priya N., mobile lead", "localizationKey": "paywall.social.rated.attribution" },
  "attributionTypography": { "...": "..." },
  "rating": {
    "symbol": "star",
    "value": 9,
    "maximum": 5,
    "step": "half",
    "size": 16,
    "filledColor": "action.primary",
    "emptyColor": "border.default"
  },
  "avatar": { "assetId": "reviewer-avatar", "size": 40 },
  "accessibility": { "label": { "default": "Customer review", "localizationKey": "paywall.social.rated.label" } }
}
```

`attribution` is **required**. An unattributed testimonial is not social proof,
and a renderer must never be left to invent or omit the source.

### The rating scale

The scale is stated precisely and bounded, in integers only.

- `symbol` is the closed constant `"star"`, following Feature List's
  single-value `marker` precedent.
- `maximum` is the number of symbols shown, in **points**, `1…10`.
- `step` is `"whole"` (one step per point) or `"half"` (two steps per point).
- `value` counts **steps, not points**, `0…20`, and a semantic rule rejects any
  `value` greater than `maximum × stepsPerPoint`.

So `{"value": 9, "maximum": 5, "step": "half"}` is four and a half stars out of
five. Integers are used throughout so that Dart, Swift, Kotlin, and JavaScript
cannot disagree about a rounded fraction — a `4.5` that four runtimes parse and
round independently is four chances to render a different number of stars.

**`rating` absent** means this testimonial carries no rating and no symbols are
drawn. It is neither a zero rating nor an unknown rating. **`avatar` absent**
means no avatar is drawn and no space is reserved for one; when present it
references a declared image asset under the same rules as an Award emblem.

Renderers announce the group in order: the rating when present, then the quote,
then the attribution. The avatar is always decorative.

### Announcing the rating

> **Narrowing correction, 2026-08-06.** This section previously said to announce
> "*value* out of *maximum*". That was wrong: `value` counts steps and
> `maximum` counts points, so a four-and-a-half-of-five announced as "9 out of
> 5". Corrected under the RC narrowing doctrine before approval.

Two rules, both mandatory.

**1. Convert steps to points.** The announced quantity is

```text
points = value / (step === "half" ? 2 : 1)
```

The conversion is exact and is never rounded: `value` is an integer and there
are one or two steps per point, so `points` is always a whole number or a whole
number and a half. `maximum` is already in points and is announced unchanged.

**2. Take the phrasing from the reserved localization key, never from a string
literal.** A renderer must not compose "out of", "of", "/", or any other
connective in any language. It reads `mosaic.a11y.rating` from the resolved
catalog and substitutes two placeholders:

```json
{ "mosaic.a11y.rating": "{{ rating.value }} out of {{ rating.maximum }} stars" }
```

Substitution is closed to `{{ rating.value }}` and `{{ rating.maximum }}`. Each
must appear exactly once in every declared translation — a translation that
drops one announces a rating with no number in it — and no other `{{ … }}`
expression is interpreted. The document's own product-template vocabulary
(`{{ product.name }}`, `{{ product.price }}`) is **not** valid here.

Word order travels with the catalog, which is the point: `"{{ rating.maximum }}
中 {{ rating.value }}"` is a conformant template.

#### Numerals are locale-independent, deliberately

Both substituted numbers use ASCII digits, `.` as the decimal separator, no
grouping separator, and exactly one fraction digit for a half step and none for
a whole one. `4.5`, `5`, `0`, `0.5`, `10`.

This is a deliberate trade against locale-correct numerals. Three renderers must
produce the same bytes for the conformance vectors to mean anything, and
platform number formatters disagree with each other — and with themselves across
OS versions — about fraction digits, separators, and default numbering systems.
Every locale's screen reader reads ASCII digits correctly, and all the locale
variation that actually changes comprehension (the words and their order) lives
in the authored template. Locale-aware numerals are a deferred protocol change,
not an oversight.

#### Conformance vectors

`protocol/fixtures/v0.3/rating-announcement.json` pins the complete expected
string for ten cases, including both step values, three authored phrasings, the
zero rating, the `value == maximum × stepsPerPoint` boundary, and an RTL
catalog. **A renderer conforms by producing `expectedAnnouncement` byte for
byte.** The file is generated from the reference implementation
(`v03RatingPoints` / `resolveV03RatingAnnouncement` in
`protocol/tools/validation-v0.3.mjs`, mirrored as `ratingPoints` /
`resolveRatingAnnouncement` in `protocol/browser/index.js`) and reconciled by
`npm run validate` against a declared floor of ten cases.

## Announcing a component: segments are never joined

> **Ruling, 2026-08-06.** Flutter was joining a component's segments with
> `". "`. Android and iOS were about to pick differently. Ruled below.

**A renderer never concatenates announced segments. There is no separator.**

`". "` is renderer-invented punctuation in exactly the way a hardcoded "out of"
is a renderer-invented word — it only looks innocuous because it is punctuation
rather than a word. It is also wrong outside Latin script: Chinese and Japanese
end sentences with `。`, Arabic and Persian use `،` and `؛`, Thai does not
separate sentences with a mark at all, and Devanagari uses `।`. A protocol that
picks one has picked English-ish typography for every locale.

Instead: **each announced segment is its own accessibility element**, inside a
container labelled by the component's authored `accessibility.label`, in the
order below. The platform's screen reader supplies whatever pause or
punctuation its locale uses, which is the thing it is actually good at — and
the user keeps the ability to navigate to one segment.

This is the same principle already in force for Tabs, where one authored label
names both the tab control and its panel rather than being composed into a
sentence.

| Component | Container role | Announced segments, in order |
| --- | --- | --- |
| `socialProof` | group | `rating` (only when a rating is declared), `quote`, `attribution` |
| `award` | group | `title`, `subtitle` (only when declared) |
| `timeline` | list | per entry, as one list item: `title`, then `description` (only when declared) |
| `button` | button | none — see below |

An absent optional segment produces **no element at all**, never an empty one.

Container roles map to `AccessibilityTraits`/`accessibilityElement(children:
.contain)` on iOS, `Modifier.semantics` with an unmerged container on Compose,
and `Semantics(container: true, explicitChildNodes: true)` on Flutter.

**Decorative, and therefore never announced and never focusable:** the Social
Proof `avatar`, the Award `emblem`, and every Timeline `marker` and the
connector. The reference implementation returns these by name so a renderer can
assert it excluded them.

### Announcing a Button, idle and busy

A Button is **one** accessibility element. Its `children` and
`inProgressChildren` are never announced separately — they are visual content,
and the Button's authored `accessibility.label` is its name in both states.

When the Button is busy:

- its **name does not change**. It stays `accessibility.label`. A control whose
  name changes mid-operation is disorienting to a screen-reader user and breaks
  UI automation that located it by name;
- the busy state is carried as the control's **value**: `accessibilityValue` on
  iOS, `stateDescription` on Compose, `Semantics(value:)` on Flutter. The string
  is the resolved `mosaic.a11y.in_progress`, never composed;
- its `inProgressChildren` are decorative. A spinner has nothing to announce,
  and an in-progress text child would duplicate the state.

Because the state occupies a distinct accessibility property rather than being
concatenated into the name, **there is no leading-or-trailing question**: each
platform announces name and value in its own conventional order. That is the
whole reason to rule it this way.

### Conformance vectors

`protocol/fixtures/v0.3/accessibility-announcement.json` pins eleven cases —
every one of the four components, both Button states, both sides of each
optional segment, and three catalogs including RTL. Each case records the
container role and value, the ordered segments, the decorative names, and
`separator: null`. **A renderer conforms by producing that structure**; a
renderer that emits a joined string has no way to match it.

Generated from `v03AccessibilityAnnouncement` in
`protocol/tools/validation-v0.3.mjs`, mirrored as `accessibilityAnnouncement` in
`protocol/browser/index.js` (with `resolvedCatalogStrings` for the catalog
lookup), and reconciled by `npm run validate` against a declared floor.

### Non-goal: focus order and announcement timing

> **Decision, 2026-08-06.** Recorded as a decision so the next person who
> notices this gap finds a ruling rather than an omission.

The contract owns **what is announced and what structure it has**. The platform
owns **when and in what order the user encounters it**. `0.3` deliberately says
nothing about:

- the order in which a user reaches components, or focus order within a screen;
- when a container is entered and its label read;
- whether, and how often, a changed value such as a busy Button's state is
  re-announced;
- whether a group is traversed as one stop or several;
- what happens to focus when a false visibility condition removes the focused
  node, or when an accepted preview revision replaces the document.

These are platform conventions, and they differ for good reasons: VoiceOver,
TalkBack, and the Flutter semantics layer each have established behaviour that
users have learned. A protocol that dictated re-announcement timing would force
three renderers to fight their platforms to conform, and would produce paywalls
that feel wrong on every one of them.

The boundary is what makes the rulings above enforceable. "Announce the rating,
then the quote, then the attribution" is a claim about **structure and content**
and a conformance vector can pin it. "Announce the rating 300ms after focus
enters" is a claim about **behaviour** that no fixture can check and no platform
would honour identically.

If a renderer finds a real divergence in this space, the outcome is a
platform-convention note in that SDK's guide, **not** a contract change. Bring
it as a contract question only if it turns out to be a disagreement about what
is announced or how it is grouped — which is this contract's business.

## Reserved accessibility strings

Some accessibility copy is announced by the protocol rather than referenced by a
component. A renderer must **never** compose it from a string literal in any
language — the 2026-08 fallback audit found hardcoded English shipping to
production on two platforms (`"Paywall unavailable"` on iOS, `"In progress"` on
Android). These keys are how that copy gets authored and translated instead.

| Key | Placeholders | Required exactly when |
| --- | --- | --- |
| `mosaic.a11y.rating` | `{{ rating.value }}`, `{{ rating.maximum }}` | any Social Proof declares a `rating` |
| `mosaic.a11y.in_progress` | none | any Button declares `inProgressChildren` |

`mosaic.a11y.in_progress` is the busy state a Button enters while a purchase or
restore is in flight. It is announced as the control's **value**, never appended
to its name — see [Announcing a
Button](#announcing-a-button-idle-and-busy).

Presence is enforced in **both** directions, like the Timeline style fields: a
reserved key is required when the document contains the feature that reads it
and **forbidden** when it does not. A missing key would leave the renderer
inventing a phrase; a lingering one is a string nothing reads, which is how
stale copy survives a redesign.

They are declared in the default catalog like any other key and may be
translated in any declared catalog. They are exempt from the unused-key check,
because no component references them by ID. A document that declares one
requires the `accessibility.reservedStrings` capability.

### Why aggregate statistics are not a Social Proof variant

"2M+ users", "Rated 4.8 by 30,000 reviewers", and "Trusted by 500 teams" are
common paywall copy, and it is tempting to add a `stats` variant here. `0.3`
deliberately does not.

A statistic has no quote, no attribution, and no per-reviewer rating. Modelling
it in this component would mean making `quote`, `attribution`,
`quoteTypography`, and `attributionTypography` all optional, at which point the
component has no invariant left and its contract says nothing a renderer can
rely on — the exact "loose variant bag" shape that makes a closed protocol stop
being closed.

A statistic is a localized string with typography, which is what **Text**
already is. An author writes `"2M+ creators build with Mosaic"` as a Text
component, and localizes the whole phrase — which is also the correct
localization boundary, because number formatting, pluralisation, and word order
around a quantity differ by locale and cannot be assembled from a numeric field
and a separate label. Should Mosaic later need a *server-supplied* live count,
that is a data-binding feature affecting every component, not a variant of this
one.

### Note on Feature List

Feature List was reviewed against the "feature list" use case during this work
and **not** changed. It is adequate: a localized ordered list with an authored
marker colour, gap, typography, and accessibility label, with per-item IDs that
are uniqueness-checked. Two gaps were identified and deliberately deferred
rather than fixed here, because both are feature additions nobody requested and
neither is a correctness defect:

1. `marker` is the single constant `"checkmark"`, so a list cannot express a
   **negated** item ("not included") for comparison paywalls. Timeline's
   three-arm marker union is the shape Feature List would adopt if this is
   wanted; the resulting two marker idioms in one protocol are a known and
   visible asymmetry, and a candidate for consolidation in `0.4`.
2. Items carry no secondary description line. Timeline now covers the
   title-plus-description shape where the sequence matters.

Its `accessibility` uses `controlAccessibility`, which requires a label, even
though a Feature List is not a control. That is cosmetic naming, not a
behavioural defect, and renaming the shared definition would churn every
consumer for no change in contract.

## Localization and locale resolution

A document declares one `localization` object: a `defaultLocale`, a
`fallbackLocale`, and a `locales` map keyed by locale tag. Catalog keys are
authored in one canonical form —
`^[a-z]{2,3}(?:-(?:[A-Z]{2}|[0-9]{3}))?$` — a lowercase language subtag with an
optional uppercase alpha-2 or numeric-3 region. Script subtags, variants,
extensions, and private-use sequences are not catalog keys. Both declared
locales must have a catalog, every referenced key must exist in the default
catalog, and each inline `default` must equal the default catalog's string.

### Requested-locale matching is case-insensitive

The requested locale comes from the device or host and arrives in whatever form
the platform uses (`en_US`, `en-US-u-rg-gbzzzz`, `PT_br`). Before lookup, a
renderer canonicalizes the requested tag to the authored grammar's form: the
value is cut at the first `@`, `.`, or `#`, underscores become hyphens, empty
subtags are dropped, the tag is truncated at the first singleton subtag, the
language subtag is lowercased, a two-letter region is uppercased, and a
three-digit region is unchanged. Matching against catalog keys is then exact.

The leading cut exists because hosts report ICU identifiers rather than language
tags: `en_US@rg=gbzzzz` (ICU keyword), `en_US.UTF-8` (POSIX charset), and
`en_US_#u-rg-gbzzzz` (Java `Locale.toString`) all denote `en-US`.

If the whole tag still cannot be canonicalized, lookup recovers the leading
language subtag — `en-US-verylongsubtag` reaches the `en` catalog. Placement
targeting deliberately does **not** recover: retargeting a malformed tag onto a
broader language changes which users match a Rule, which is a monetization
decision, whereas here the chain would otherwise fall through to the document's
own fallback and the worst outcome of recovery is a less-specific translation of
the author's own copy. A value from which not even a language subtag can be
recovered contributes no candidate.

This is the same canonical form Placement targeting applies to
`application.locale`, deliberately: the two subsystems must not disagree about
what "the same locale" is. Case-insensitivity introduces no ambiguity, because
the authored grammar admits exactly one spelling of any tag — two catalog keys
can never differ only by case — and BCP 47 tags are case-insensitive by
RFC 5646. A resolver that compared raw platform strings would simply miss the
one catalog that exists.

This is a clarification of frozen `0.3` behaviour, not a change to it. No
authored document changes meaning, no declared catalog stops being reachable,
and no requested locale that resolved to a catalog before resolves to a
different one now: canonicalization only lets requested spellings that
previously fell through to `fallbackLocale` reach the catalog they always
denoted.

### Candidate chain

Resolution walks an ordered candidate list: the canonical requested tag, its
base language subtag, the declared `fallbackLocale`, then the declared
`defaultLocale`. Candidates that no catalog declares are skipped; a key missing
from the resolved catalog falls through the remaining candidates and finally to
the component's inline `default`, which always exists. A requested locale that
canonicalizes to nothing usable contributes no candidate rather than matching
anything. Direction derives from the first declared candidate.

`0.3` defines **no language+region reduction step**. A requested `zh-Hans-CN`
reduces to `zh`, never to `zh-CN`, because its base language is `zh`. See the
Protocol entry in [`docs/known-limitations.md`](../known-limitations.md).

The reference implementation is
`protocol/tools/locale-resolution-v0.3.mjs`, and the cross-SDK corpus is
`protocol/fixtures/v0.3/locale-resolution.json`.

The corpus's `expectedCandidates` is normative for **lookup order only**: a
renderer must consult catalogs in that relative order and stop at the first
declared candidate. It is not a required public API shape. Exposing the full
ordered list including keys the document does not declare, and exposing only the
declared subset, are both conformant — what must match is
`expectedCatalog`, the catalog resolution selects.

## Capabilities and fallback

Capabilities are exact and derived only when the corresponding feature occurs.
`0.3` adds five over `0.2`:

```text
component.tabs            component.timeline
component.award           component.socialProof
condition.tabVisibility   accessibility.reservedStrings
```

`condition.tabVisibility` is derived only from a `visibility` whose `mode` is
`"tab"`, exactly as `condition.switchVisibility` is derived from `"switch"`. A
document containing a Tabs component that nothing is conditioned on requires
`component.tabs` and not `condition.tabVisibility`.

### Tabs requires no style capability for its two states

> **Ruling, 2026-08-06.** Studio observed that `style.productCardStates` is not
> derived for Tabs even though Tabs uses the same `selectionStyles` contract,
> and asked whether that was an omission. It is not.

**A capability that can never vary independently of another capability carries
no information, and Mosaic does not mint one.**

`styles` is a **required** property of `tabs`. A renderer therefore cannot
declare `component.tabs` and decline authored two-state tab styling — there is
no conformant Tabs document without it. `component.tabs` already *is* the claim
"I can render authored Default and Selected tab appearance", so a separate
`style.tabStates` would be present in exactly the documents where
`component.tabs` is present and absent in exactly the documents where it is
absent.

This satisfies the distinguishability requirement directly: a renderer that
supports Product Card states but not Tab states declares `component.productCard`
and omits `component.tabs`. Nothing is lost by not minting a second signal.

Sharing the `selectionStyles`, `selectionStateStyle`, and
`selectionStateStyleOverride` definitions between Product Card, Product Badge,
and Tabs is a statement that the three have the **same style contract**. It is
not a statement that they share a capability. Capabilities gate what a renderer
can draw; definitions describe how it is authored.

#### `style.productCardStates` is a legacy co-derived signal

For the same reason, `style.productCardStates` carries no independent
information either: it is derived exactly when `component.productSelector`,
`component.productCard`, or `component.productBadge` is derived, because
`styles` is required on all three. It is retained in `0.3` because removing it
would churn four teams mid-implementation for no behavioural gain, and a test
pins its exact co-derivation so it cannot quietly acquire a second meaning —
such as silently starting to gate Tabs. **It is a candidate for removal in
`0.4`**, and no renderer should treat it as a signal distinct from the three
component capabilities.

### Deriving capabilities: call the reference implementation

Capabilities are derived, not authored, and a hand-maintained mirror of the
derivation is rejected at delivery rather than caught by a typechecker. The
`protocol/browser/index.js` runtime exports the reference implementation and
every table it uses:

| Export | What it is |
| --- | --- |
| `expectedDocumentCapabilities(document)` | the capability names a document requires, in canonical order |
| `requiredCapabilitiesFor(document)` | the same, shaped for `compatibility.requiredCapabilities` |
| `capabilityNames` | the canonical ordering, taken from the schema enum |
| `capabilityByComponentType` | component type to the capability it requires |
| `colorFieldNames` / `usesColor(value)` | the colour-field table and the predicate that reads it |
| `reservedAccessibilityKeys` | the reserved-key table, with its placeholders and consumption predicates |
| `accessibilityAnnouncement(node, {strings, state})` | the ordered announced segments, container role and value, and decorative names |
| `resolvedCatalogStrings(localization, locale)` | the catalog a requested locale resolves to |
| `ratingPoints` / `resolveRatingAnnouncement` | the rating conversion and its substitution |
| `paywallContractVersion` | `"0.3"` |

Consumers must call these rather than copy them. A test pins each export against
the derivation that uses it — an exported colour field the predicate does not
consult, or an ordering that diverges from the schema enum, fails the protocol
gate.

Existing `asset.bundledImage`, styling, component, action, localization,
accessibility, and runtime capabilities remain exact. A client missing any
required capability rejects the whole candidate before replacing its last
accepted document. There is no partial style or component rendering.

Runtime fallback is separate from compatibility rejection: unavailable media
uses poster/colour fallback and diagnoses; Fill on an unbounded axis uses Fit
and diagnoses; root Navigate Back remains a no-op diagnostic. Failure still
resolves through last accepted, bundled fallback, then configuration
unavailable.

## Explicit deferrals

`0.3` intentionally defers multiple fills/effects/shadows, video audio or
controls, arbitrary animation, freeform canvas coordinates in the document,
custom sheet transitions/detents, project/server design libraries, horizontal
Timeline orientation, Feature List negated markers, locale-aware numerals in
reserved accessibility strings, and any aggregate-statistic component. Those features require a later reviewed protocol change.
