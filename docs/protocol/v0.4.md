# Mosaic Protocol 0.4 — Motion

## Status and authority

Protocol `0.4` is a **draft**. It carries no compatibility guarantee, it may
change without a version bump, and nothing produces or consumes it in
production. `protocol/compatibility/v0.4.json` records `status: "draft"` and
deliberately carries no `releaseCandidate` label; a draft has not reached the
state that label describes.

`0.4` is a **pure superset of `0.3`** apart from two removals `0.3` itself
named for this version. Paywall Protocol `0.3` remains the release candidate
and remains untouched by this work: a `0.3` document is still read by a `0.3`
reader, `0.3` fixtures are unchanged, and the `0.3` schema, manifest, and
validator are byte-identical to what they were before `0.4` existed.

The gate was opened by an explicit owner decision recorded in
[`docs/product/motion-exploration.md`](../product/motion-exploration.md). That
document also records that the sequencing recommendation — finish `0.3` and
Phase 9C first — was considered and **overridden**, and that the resulting
risk is accepted: any narrowing correction the `0.3` renderer work surfaces
must be absorbed into `0.4` as well. See
[ADR-0027](../architecture/decisions/0027-protocol-0.4-motion.md).

Canonical artifacts:

- `protocol/schema/v0.4/paywall.schema.json`
- `protocol/schema/v0.4/compatibility-manifest.schema.json`
- `protocol/compatibility/v0.4.json`
- `protocol/fixtures/v0.4/complete-paywall.json`
- `protocol/fixtures/v0.4/motion-frames.json`
- `protocol/fixtures/v0.4/invalid/`
- `protocol/tools/validation-v0.4.mjs`

### What this slice does not include

`0.4` is the **contract**. The three native renderers, Studio authoring, and
the backend capability partitioning are later waves. In particular the backend
capability check in
`apps/api/internal/hostedpublishing/capability_request.go` must eventually
partition on the manifest `fallback` so that a reader missing a `motion.*`
capability receives the release rather than a capability-missing refusal. That
integration point is **flagged and deliberately not modified** by this slice.

Local Preview `0.4` has since landed as its own draft; see
[Local Preview](#local-preview-04-has-landed).

## Why motion, and why this much of it

The agentic plan already names animation metadata as a protocol
responsibility, and `0.3` explicitly defers "arbitrary animation" to a later
reviewed change. This is that change, deliberately kept small.

The market position `0.4` takes is **less motion than a webview competitor,
but native, accessible, and identical on three platforms**. The primitives are
chosen for what survives that constraint, not for what is expressible. There
is no credible public evidence that paywall motion lifts conversion; the
defensible claims are attention capture and perceived quality, and the
counter-signal — visual-only paywall tests have the lowest experiment win rate
— is respected rather than argued away. The plan is to ship the primitives,
measure them through Phase 7 Experiments, and publish the result.

## The rule that makes it safe

> **Every animation's terminal state is byte-identical to the static
> rendering.** This is normative and holds in every branch of the reference
> resolver.

Everything else in this document follows from that one sentence:

- `renderWithoutMotion` is **provably lossless**, because the thing a
  motion-less renderer draws is the thing a motion-capable renderer ends at;
- reduced motion is always available as "be at the end already", with no
  second set of authored values to keep in sync;
- the `t = end` conformance golden **is** the existing static golden, and so is
  the reduced-motion loop golden — two assertions fall out for free;
- a motion bug can never leave a price, a disclosure, or a purchase control
  unreachable, because there is no reachable state in which motion is running
  and finished values do not exist.

The reference resolver short-circuits the terminal state rather than
approaching it, so no accumulation of rounding can leave a price at `0.9999`
opacity or a card at `1.0001` scale.

## Motion tokens

`designSystem` gains a fourth catalog, `motions`, mirroring `colors`,
`backgrounds`, and `shadows` exactly. It is **required** and may be empty.

```json
{
  "designSystem": {
    "colors": [],
    "backgrounds": [],
    "shadows": [],
    "motions": [
      {
        "id": "motion-entrance",
        "name": "Entrance",
        "value": { "type": "motion", "durationMilliseconds": 240, "easing": "decelerate" }
      },
      {
        "id": "motion-entrance-alias",
        "name": "Entrance alias",
        "value": { "type": "motionToken", "id": "motion-entrance" }
      }
    ]
  }
}
```

A motion is referenced as `{ "type": "motionToken", "id": "motion-entrance" }`
or authored inline as `{ "type": "motion", "durationMilliseconds": …,
"easing": … }`, mirroring the `inlineShadow` / `shadowTokenReference` pair.

Duration and easing are **one composite** because neither is meaningful
without the other: a duration with no curve and a curve with no duration are
both half a decision. Durations are **integers**, `0…2000`, following the
`0.3` doctrine that Dart, Swift, Kotlin, and JavaScript must not disagree
about a rounded fraction. `0` is legal and means the change applies instantly.

IDs and display names are unique inside the catalog, token-to-token references
are permitted, every reference must resolve, and the graph must be acyclic —
the same rules the other three catalogs carry.

### Unused motion tokens are rejected; unused colours are not

This is a **deliberate asymmetry**, called out here so that nobody later
"fixes" the colour, background, and shadow catalogs to match it.

An unreferenced colour token is inert. Its only risk is being wrong, and being
wrong about a colour nothing draws costs nothing.

An unreferenced **motion** token is different, because the safety constraint on
a motion lives at its **reference site**, not at its declaration. The
flash-safety floor is checked where a `loop` names a curve. A motion token that
nothing references has therefore never been checked against anything, and it
sits in the catalog looking like an approved timing value. The next author to
reach for it inherits a duration that no rule has ever seen. That is a latent
accessibility decision, not an inert value, so the validator rejects it.

A token reached only through another token counts as used.

## Easing: four presets, and the reason there are only four

`easing` is one of `linear`, `standard`, `decelerate`, `accelerate`. The
control points are **normative** and fixture-pinned:

| Preset | Cubic-bezier control points | Use |
| --- | --- | --- |
| `linear` | `0, 0, 1, 1` | no shaping; `y = x` exactly |
| `standard` | `0.4, 0, 0.2, 1` | movement that starts and ends on screen |
| `decelerate` | `0, 0, 0.2, 1` | something entering; fast in, settles |
| `accelerate` | `0.4, 0, 1, 1` | something leaving; slow out, speeds up |

These map exactly onto SwiftUI `timingCurve(_:_:_:_:)`, Compose
`CubicBezierEasing`, and Flutter `Cubic`, which is the whole reason for
choosing cubic beziers: it is the one faithfully portable curve family across
the three renderers.

**Springs are excluded.** They have three different parameterizations and
three different settling rules across the supported platforms, and matching
them across renderers means reimplementing the ODE and then fighting each
platform's own implementation.

**Authored control points are excluded.** An out-of-range `y` fakes a spring,
and overshoot is exactly where the three platforms clamp opacity and scale
differently. Every preset above is monotonic and stays within `0…1`; a test
asserts it. Widening to authored curves later is cheap. Retracting them would
not be.

## Three primitives, constrained by trigger

A node may carry a `motion` block. Which members it may carry depends on what
the node is:

| Trigger | Allowed on | Document-rejecting rule |
| --- | --- | --- |
| `appear` | any node except the screen Scroll Container | a node with `appear` may not descend from another node with `appear` |
| `selection` | `productSelector`, `tabs` | — |
| `loop` | `button` | at most one per **screen** |

The screen Scroll Container is excluded for the same reason `0.3` excludes it
from `sizing`: it is viewport-owned rather than authored.

### `appear`

```json
{
  "motion": {
    "appear": {
      "effect": "fadeRise",
      "riseLogicalSize": 12,
      "curve": { "type": "motionToken", "id": "motion-entrance" },
      "delayMilliseconds": 80
    }
  }
}
```

Plays once when the node first enters a screen. `effect` is `fade` or
`fadeRise`; `riseLogicalSize` is **required with `fadeRise` and forbidden with
`fade`**, enforced by the schema rather than by prose. It is bounded at `64`
logical units: a rise longer than the component it moves reads as a fly-in
rather than an entrance, and a large authored translation is where
transform-versus-layout divergence between three renderers becomes visible.
The node travels *to* its laid-out position, so its final geometry is its
static geometry.

`delayMilliseconds` is how stagger is authored. Siblings with `0`, `80`, and
`160` produce a staggered reveal. There is **no stagger sugar** in `0.4` — see
[deferrals](#explicit-deferrals).

**Nested `appear` rejects the document.** Two entrance opacities multiply, and
the three renderers compose that product at different points in their
pipelines: rejecting is cheaper than pinning an arithmetic that no platform
agrees on, and an author who wants a group to fade in puts the `appear` on the
group.

### `selection`

```json
{ "motion": { "selection": { "curve": { "type": "motionToken", "id": "motion-selection" } } } }
```

Interpolates the authored Default and Selected box styles when the runtime
selection changes. Allowed only on the two components that own runtime
selection state.

The interpolable field list is **closed**:

| Field | Behaviour |
| --- | --- |
| `background` | interpolates when both endpoints are `{"type":"color"}` with canonical `#RRGGBBAA` literals; otherwise switches at `t = 0.5` |
| `border.color` | as above |
| `border.width`, `cornerRadius`, `opacity` | always interpolate |
| `shadow` | interpolates when both endpoints are inline shadows; colour follows the colour rule |
| `background` *kind* change, `padding` | **switch discretely at `t = 0.5`** |

A semantic colour name resolves against the renderer's theme and a
`colorToken` resolves against the document; neither has a numeric value the
protocol can average, so rather than invent one, the change applies at the
half-way point. Padding is structural: interpolating it relayouts the subtree
every frame on three layout engines that disagree about when that is legal.

Tabs `selection` animates the **tab control's style, not the panel swap**.
`0.3` visibility semantics remove a hidden node from layout, the accessibility
tree, and focus order; animating a removal would require a "present but not
focusable" third state that does not exist. Exit animation is later work.

### `loop`

```json
{
  "motion": {
    "loop": {
      "effect": "pulse",
      "scaleAmplitude": 0.04,
      "opacityAmplitude": 0.12,
      "curve": { "type": "motionToken", "id": "motion-pulse" },
      "repeat": { "count": 3 }
    }
  }
}
```

A bounded call-to-action pulse. One cycle is an excursion out and back: scale
runs `1 → 1 + scaleAmplitude → 1`, opacity runs `O → O × (1 −
opacityAmplitude) → O`, both driven by the same eased phase, peaking at the
half-cycle. The excursion is `0` at **both ends of every cycle**, so a cycle
boundary is the static rendering rather than a near miss.

**`repeat.count` is `1…5`. There is no `forever` mode anywhere in the
schema.** This is an owner ruling on accessibility grounds. An unbounded pulse
would rely on the operating system's reduce-motion switch as its WCAG 2.2.2
stop mechanism, which means a user who has not enabled that switch has no stop
mechanism at all. A bounded count needs no stop control because it stops.

#### Opacity floor semantics

`opacityAmplitude` is a **fraction of the node's resolved static opacity**, not
an absolute value. The floor is `resolvedOpacity × (1 − opacityAmplitude)` and
the rest value is `resolvedOpacity` exactly.

This matters twice. It keeps the terminal-state rule exact for a node that
authored `appearance.opacity: 0.8` — the pulse rests at `0.8`, not at `1.0`.
And it means the pulse can never drive a price fainter than the author asked
for: the ceiling of `0.2` puts the floor at no less than 80% of whatever the
static rendering already was.

`opacityAmplitude` may be `0`, which is a pulse that scales without dimming.
`scaleAmplitude` must be positive: a pulse that does not scale is not a pulse.

## Flash safety is schema- and validator-enforced, not advised

| Bound | Value | Why |
| --- | --- | --- |
| `loop` curve duration | ≥ **500 ms** | caps the pulse's fundamental at 2 Hz and its perceived rate at 1 Hz, an order of magnitude below the three-per-second threshold WCAG 2.3.1 draws |
| `scaleAmplitude` | ≤ **0.06** | a 6% excursion is noticeable and not startling; larger excursions overlap neighbouring content and change perceived hit targets |
| `opacityAmplitude` | ≤ **0.2** | keeps the floor at ≥ 80% of the static opacity, well clear of a flash |
| colour loops | **inexpressible** | a looping colour change *is* the flash primitive; `pulse` carries only scale and opacity, so it is excluded structurally rather than by a rule someone can argue with |
| `repeat.count` | ≤ **5** | bounded above by construction |

The duration floor is checked in the **semantic** layer rather than the schema
because the duration lives on a token and the constraint belongs to the
reference site: the same 240 ms token is legitimate for an entrance and
illegitimate for a pulse.

**Motion never touches the accessibility tree.** A node mid-entrance is already
present, focusable, and announceable; a pulsing button announces exactly what a
static one announces. There is no motion-conditional accessibility state and no
way to author one.

## The reduced-motion contract

This is **protocol-mandated**, not renderer-interpreted. The signal is
injected at the renderer boundary like the clock, so it is testable.

### Platform signal mapping

| Platform | Signal | Reduced motion when |
| --- | --- | --- |
| iOS / SwiftUI | `UIAccessibility.isReduceMotionEnabled` (`accessibilityReduceMotion`) | `true` |
| Android / Compose | `Settings.Global.ANIMATOR_DURATION_SCALE` | `0` |
| Flutter | `MediaQuery.disableAnimationsOf(context)` | `true` |
| Studio / web chrome | `prefers-reduced-motion: reduce` | matches |

### Per-primitive behaviour

| Primitive | Under reduced motion |
| --- | --- |
| `appear` | **opacity only.** The transform is dropped; `translateLogicalSize` is `0` at every instant, including the start frame. |
| `selection` | **applies instantly.** The frame at every elapsed time is the resolved Selected style exactly. |
| `loop` | **fully disabled.** The node sits at rest — scale `1`, opacity multiplier `1`, which is the static rendering. |

The `appear` ruling is what resolves the iOS-replace versus Android-remove
divergence without per-platform clauses: **the contract owns *what* changes and
the platform owns *how long*.** A renderer may shorten or zero the duration of
the remaining opacity change according to its platform's convention. What is
normative is that no transform occurs and that the terminal state is unchanged.

### Video backgrounds under reduced motion

> **Ruling.** `0.3` specifies video backgrounds as "always muted, autoplaying,
> looping, and control-free" and no SDK reads the platform reduced-motion
> signal. Apple's App Store Reduced Motion evaluation criteria cover "any other
> ongoing motion", so a Mosaic paywall can invalidate a customer's
> accessibility declaration. The owner ruled that this ships as **specified
> `0.4` behaviour**, not as a `0.3` defect patch. The live exposure remains
> open until `0.4` lands and is accepted.

**Under reduced motion, a video background does not play.** The renderer
renders the declared `posterAssetId` if that image is available, and otherwise
the declared `fallbackColor`. No frame of the video is shown, playback is not
started and paused, and no control is offered.

This is the same resolution order the existing `missingMediaBackground` policy
already uses, which is deliberate: the reduced-motion path reuses a path that
three renderers have already implemented rather than introducing a fourth
outcome. It is recorded machine-readably in the manifest as
`readerPolicy.reducedMotionVideoBackground:
"renderPosterThenFallbackColorWithoutPlayback"`.

A video background authored with no `posterAssetId` degrades to its fallback
colour under reduced motion. Authors who care about that case declare a poster;
the protocol does not make one mandatory, because a colour is a legitimate
answer and a required-but-ignorable field is worse than an optional one.

Renderer implementation of this ruling is a later wave.

## The enhancement tier

Every capability in every Mosaic contract before this one carries `fallback:
"rejectDocument"` as a schema `const`, and server-side stripping of material a
reader cannot understand is doctrine-forbidden. Motion introduces the first
exception.

Three capabilities — `motion.appear`, `motion.selection`, `motion.loop` —
carry **`renderWithoutMotion`**. Everything else still carries
`rejectDocument`, and a validator asserts that partition rather than trusting
review to notice a drift.

The value is named for **motion specifically**, not generically. A
`renderWithoutFeature` would be an invitation to relitigate the
no-partial-rendering doctrine once per feature; a motion-shaped name cannot
spread by imitation.

The reader policy splits accordingly:

```json
{
  "unsupportedRequiredCapability": "rejectDocument",
  "unsupportedEnhancementCapability": "renderStaticDocument"
}
```

A reader missing `component.tabs` still rejects the whole document. A reader
missing `motion.loop` renders the document **statically and completely** —
which the terminal-state rule guarantees is the full authored design.

Granularity is three capabilities rather than one, by the `0.3`
distinguishability test: a renderer that can cross-fade a selection but has no
per-node entrance driver is a real renderer, and one capability could not say
so. Capability derivation is unchanged in shape and needs no special case: a
`motion.*` capability is derived exactly when that motion occurs, and the
existing unused-capability rule actively protects the tier by rejecting a
document that claims motion it does not author.

## Conformance: the frame vectors

Motion is the first thing in the protocol whose contract is a *value at an
instant* rather than a value. Prose cannot pin that, and three renderers will
not agree by coincidence.

`protocol/fixtures/v0.4/motion-frames.json` records, for every trigger, effect,
and easing preset, the exact frame a renderer must be showing at `t = 0`, a
quarter, a half, three quarters, and the end — plus the reduced-motion answer
for each, an authored-delay case, and the per-cycle phases of the pulse.

- Generated by `resolveV04MotionFrame` in `protocol/tools/validation-v0.4.mjs`
  and reconciled against it by `npm run validate`. **The tool and the fixture
  cannot drift**: a hand edit to either fails the gate.
- Mirrored as `resolveMotionFrame` in `protocol/browser/index.js`, with a test
  that drives every frame of every case through both implementations.
- Numbers carry **four decimal places**. The stated tolerance is
  `toleranceAbsolute: 0.001` — continuous interpolation cannot be byte-pinned
  across three platform bezier solvers, and 1e-3 is two orders of magnitude
  below perceptibility.
- The last frame of every case is the terminal state, and the validator rejects
  a case that never reaches it.

```js
resolveV04MotionFrame(motion, {
  trigger,               // "appear" | "selection" | "loop"
  elapsedMilliseconds,   // whole, non-negative; throws otherwise
  reducedMotion,         // boolean
  resolvedFrom,          // selection only; required there, forbidden elsewhere
  resolvedTo,
});
```

The resolver is pure and integer-in, following the `resolveV03CountdownState`
precedent: a clock that cannot be trusted **throws** rather than resolving,
because arithmetic on a bad clock yields a frame that reads back as plausible.
The `curve` must already be resolved to an inline motion; a `motionToken`
reference throws, because a resolver that silently accepted an unresolvable
token would return the frame for a duration nobody authored.

Renderers additionally need an injectable **motion driver** — Compose
`mainClock.advanceTimeBy`, Flutter `tester.pump(duration)`, iOS driving
progress directly — and every existing static golden must be captured with the
driver disabled. Android's SHA-256 zero-tolerance goldens make that
non-optional rather than advisable. That work belongs to the renderer wave.

## Bundled `0.3` cleanups

`0.3` flagged two items for this version. Both are applied here, because a
version bump has a fixed cost and paying it twice for two one-line cleanups is
worse than paying it once.

### `style.productCardStates` is removed

`0.3` records it as "a legacy co-derived signal": it is derived exactly when
`component.productSelector`, `component.productCard`, or
`component.productBadge` is derived, because `styles` is required on all three.
A capability that can never vary independently of another capability carries no
information. `0.3` kept it only to avoid churning four teams mid-implementation
and named it for removal here.

It is gone from the schema enum, the manifest, and the derivation. A `0.4`
document that declares it is rejected as an unknown capability.

### One marker vocabulary

`0.3` notes that Feature List's `marker` is the single constant `"checkmark"`,
so a list cannot express a **negated** item — "not included" on a comparison
paywall — and that Timeline's three-arm marker union is the shape Feature List
would adopt, with the two idioms in one protocol being "a known and visible
asymmetry, and a candidate for consolidation in `0.4`".

`0.4` consolidates. One shared `marker` union — `{"kind":"dot"}`,
`{"kind":"ordinal"}`, `{"kind":"icon","name":<iconName>}` — is used by both
components. Feature List's component-level `marker` is the list's default
glyph, and an **item** may override it:

```json
{
  "type": "featureList",
  "marker": { "kind": "icon", "name": "checkmark" },
  "markerColor": "action.primary",
  "items": [
    { "id": "unlimited-projects", "text": { "…": "…" } },
    { "id": "priority-support", "marker": { "kind": "icon", "name": "close" }, "text": { "…": "…" } }
  ]
}
```

An absent item `marker` means the item carries the list's marker. It is never a
request for no glyph.

Marker **colour and size stay component-level**, exactly as they are on
Timeline. A per-item marker colour — a green tick beside a red cross — is a
second axis and a deliberate deferral, not an oversight: the negated case is
carried by the glyph, and adding a per-item colour without a per-item size
would be a half-measure that the next redesign has to undo.

## Migration from `0.3`

The migration is mechanical. `protocol/fixtures/v0.4/` was produced from
`protocol/fixtures/v0.3/` by exactly these steps, applied by a script, so that
"mechanical" is a demonstrated property rather than a claim.

1. `schemaVersion`: `"0.3"` → `"0.4"`.
2. Every entry in `compatibility.requiredCapabilities`: `version` `"0.3"` →
   `"0.4"`.
3. **Remove** any `{"name": "style.productCardStates"}` entry.
4. Add `"motions": []` to `designSystem`. The catalog is required and may be
   empty.
5. Every Feature List: `"marker": "checkmark"` → `"marker": {"kind": "icon",
   "name": "checkmark"}`.

Nothing else changes. A `0.3` document that has been through those five steps
is a valid `0.4` document with no motion, and renders identically.

Motion is then **purely additive**: adding a `motions` catalog and `motion`
blocks changes no static rendering, because of the terminal-state rule.

`0.4` does **not** read `0.3` documents and `0.3` does not read `0.4`
documents. Versions are exact identifiers; a reader declaring `0.4` accepts
only `0.4`. When `0.4` becomes deliverable, publishing emits a `0.3`
representation by projection at publish time — the established Configuration
Delivery pattern — so one authored document can serve both reader generations.
The projection drops `motion` blocks and the `motions` catalog, which is
lossless *as a rendering* for exactly the same reason `renderWithoutMotion` is.

## What `0.4` does not change

The announcement contract, the rating scale and its reserved localization keys,
locale resolution, product templates, visibility semantics, navigation, and
every `0.3` component are unchanged. The `0.4` accessibility-announcement
corpus travels with the canonical document because it names components by ID,
but it is reconciled against the **`0.3` reference implementation** rather than
a `0.4` copy of it: two implementations of one unchanged contract is exactly
the drift this repository has been bitten by before. The rating-announcement
and locale-resolution corpora are standalone and are not duplicated for the
same reason.

## Explicit exclusions, with reasons

These are excluded from the contract, not merely absent from it.

| Excluded | Reason |
| --- | --- |
| **Lottie / Rive** | a state machine is remote executable behaviour, a direct violation of the no-executable-code-in-remote-configuration rule; plus three native runtime dependencies and content no validator can inspect |
| **Keyframe timelines** | a mini animation language, which is the thing a declarative protocol exists to avoid |
| **Scroll-linked motion, parallax** | needs a scroll-state binding the protocol deliberately does not expose, and platform scroll physics differ by construction. There are consequently no "parallax limits" to specify: there is no parallax |
| **Springs** | three parameterizations, three settling rules; matching them means reimplementing the ODE and fighting each platform's own |
| **Authored cubic-bezier control points** | out-of-range `y` fakes a spring, and overshoot is where platform clamping of opacity and scale diverges |
| **Screen and sheet transitions** | platform-owned; the same boundary `0.3` drew for focus order |
| **Shimmer** | moving gradient masks are where cross-platform fidelity dies, and on a CTA a shimmer reads as skeleton-loading |
| **Colour loops** | a looping colour change *is* the flash primitive; excluded structurally by `pulse` carrying only scale and opacity |
| **Countdown-conditional motion** | deferred: it adds a second time axis to conformance. Authored *urgency* motion is additionally a store-policy risk under Apple's fake-urgency guidance and Google Play's deceptive-behaviour policy, and the recommendation is permanent exclusion rather than deferral |

## Explicit deferrals

Deferred means "not now", not "never". Each needs a reviewed protocol change.

- **Exit and removal animation.** Requires a "present but not focusable" third
  visibility state that does not exist. `0.5` at the earliest.
- **Stagger sugar.** `0.4` has authored `delayMilliseconds` and nothing else.
  A `stagger` property on a container is convenience over a mechanism that
  already works, and it is easy to add once real documents show what the
  common shape is.
- **Carousel auto-advance.** A component behaviour rather than a motion
  primitive. If it is ever built it needs a pause affordance per WCAG 2.2.2.
- **Authored cubic-bezier control points.** Presets are cheap to widen and
  impossible to retract; the decision is reversible in this direction only.
- **Per-item Feature List marker colour and size.**
- **Locale-aware numerals** in reserved accessibility strings, carried forward
  from `0.3`.
- **Horizontal Timeline orientation**, carried forward from `0.3`.

built. Local Preview `0.3` is unchanged and still correct for `0.3` drafts.

All seven items this section originally enumerated are delivered; see
[Local Preview 0.4](local-preview-v0.4.md) for the contract.

   (`$ref` retargeted to `urn:mosaic:protocol:schema:v0.4:paywall`, `$id` and

   `compatibility-manifest.schema.json`.
2. `protocol/compatibility/local-preview/v0.4.json`, `status: "draft"`.
3. The **runtime-state motion member**: the accepted-revision runtime state

   is not strobed once per keystroke.
4. `protocol/fixtures/local-preview/v0.4/` — `local-project.json`,
   `session-flow.messages.json`, and `accepted-revision-runtime-reset.json`
   updated with the new member.
5. `protocol/tools/preview-validation-v0.4.mjs` and its wiring into
   `validate.mjs`.
6. The WebSocket subprotocol `mosaic.local-preview.v0.4` in
   `browser/index.js` negotiation, with `0.4` added to
   `localPreviewVersionPreference` ahead of `0.3`.
7. `docs/protocol/local-preview-v0.4.md` and a `versioning.md` update.

Two things the checklist did not anticipate, both recorded here because the next
reader will otherwise re-derive them:

- **`playedAppearScreens: []` is the value of a *first* acceptance, not of
  every acceptance.** Written as a reset value it contradicts the suppression
  rule it sits beside: a member that resets to empty on every acceptance
  replays every entrance on every keystroke, which is the exact defect the rule
  exists to prevent. It is the one runtime member an acceptance carries
  forward, filtered through the accepted document's screens. The fixture pins
  all three states — before, after, and first — rather than the two `0.3`
  pinned.
- **Item 6 is not self-contained.** Negotiating `0.4` without also making
  `decideLocalPreviewDraftDelivery` version-aware yields a relay that agrees on
  a subprotocol and then withholds every draft on it, because the preview
  capability check was pinned to the literal `"0.3"`. The delivery decision and
  the message/local-project readers dispatch on version too.

### What Local Preview 0.4 does not include

The three native preview clients and Studio's preview surface are later waves.
This slice is the contract, its fixtures, its validator, and the browser
runtime that Studio builds on.
