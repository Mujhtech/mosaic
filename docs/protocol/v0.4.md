# Mosaic Protocol 0.4 — Motion

## Status and authority

Protocol `0.4` is a **draft**. It carries no compatibility guarantee, it may
change without a version bump, and nothing produces or consumes it in
production. `protocol/compatibility/v0.4.json` records `status: "draft"` and
deliberately carries no `releaseCandidate` label; a draft has not reached the
state that label describes.

`0.4` is a **pure superset of `0.3`** apart from two removals `0.3` itself
named for this version. Paywall Protocol `0.3` remains the release candidate
and remains untouched by this work: a `0.3` document is still read by a `0.3`
reader, `0.3` fixtures are unchanged, and the `0.3` schema, manifest, and
validator are byte-identical to what they were before `0.4` existed.

The gate was opened by an explicit owner decision recorded in
[`docs/product/motion-exploration.md`](../product/motion-exploration.md). That
document also records that the sequencing recommendation — finish `0.3` and
Phase 9C first — was considered and **overridden**, and that the resulting
risk is accepted: any narrowing correction the `0.3` renderer work surfaces
must be absorbed into `0.4` as well. See
[ADR-0027](../architecture/decisions/0027-protocol-0.4-motion.md).

Canonical artifacts:

- `protocol/schema/v0.4/paywall.schema.json`
- `protocol/schema/v0.4/compatibility-manifest.schema.json`
- `protocol/compatibility/v0.4.json`
- `protocol/fixtures/v0.4/complete-paywall.json`
- `protocol/fixtures/v0.4/screen-round-trip.json`

- `protocol/fixtures/v0.4/invalid/`
- `protocol/tools/validation-v0.4.mjs`

### What this slice did not include, and what has since landed

`0.4` opened as the **contract** alone, with the renderers, Studio, and the
backend named as later waves. Most of that has since landed, and this section
records the difference rather than restating the original list:

- **The three native renderers implement motion.** Flutter (`d0b2e2b`), Android
  (`ed02c07`), and iOS (`b1c5bbb`) each carry a motion renderer, an injectable
  driver, and a frame-vector conformance suite.
- **Studio authors motion.** The `0.4` design-system motion catalog, the
  per-node motion inspector, and the `0.3 → 0.4` upgrade action landed in
  `f8b15b8`. Studio's **live preview** surface is still a later wave; see
  [Local Preview 0.4](local-preview-v0.4.md#browser-runtime-support).
- **The backend partitions capabilities on the manifest.** `capability_request.go`
  no longer treats every capability as `rejectDocument`; it partitions on the
  manifest `fallback` so a reader missing a `motion.*` capability receives the
  release rather than a capability-missing refusal (`cadfd1e`).

One backend integration point remains **flagged and deliberately not
implemented**: publish-time projection must apply the [projectability
rule](#the-projectability-rule) and decline to emit a `0.3` representation it
cannot construct faithfully, following the `safeV1Projection` precedent in
`apps/api/internal/hostedpublishing/service_publish.go`.

Delivering a `0.4` document to an SDK is separately blocked; see [Configuration
Delivery cannot yet carry `0.4`](#configuration-delivery-cannot-yet-carry-04).

Local Preview `0.4` has since landed as its own draft; see
[Local Preview](#local-preview-04-has-landed).

## Why motion, and why this much of it

The agentic plan already names animation metadata as a protocol
responsibility, and `0.3` explicitly defers "arbitrary animation" to a later
reviewed change. This is that change, deliberately kept small.

The market position `0.4` takes is **less motion than a webview competitor,
but native, accessible, and identical on three platforms**. The primitives are
chosen for what survives that constraint, not for what is expressible. There
is no credible public evidence that paywall motion lifts conversion; the
defensible claims are attention capture and perceived quality, and the
counter-signal — visual-only paywall tests have the lowest experiment win rate
— is respected rather than argued away. The plan is to ship the primitives,
measure them through Phase 7 Experiments, and publish the result.

## The rule that makes it safe

> **Every animation's terminal state is byte-identical to the static
> rendering.** This is normative and holds in every branch of the reference
> resolver.

Everything else in this document follows from that one sentence:

- `renderWithoutMotion` is **provably lossless**, because the thing a
  motion-less renderer draws is the thing a motion-capable renderer ends at;
- reduced motion is always available as "be at the end already", with no
  second set of authored values to keep in sync;
- the `t = end` conformance golden **is** the existing static golden, and so is
  the reduced-motion loop golden — two assertions fall out for free;
- a motion bug can never leave a price, a disclosure, or a purchase control
  unreachable, because there is no reachable state in which motion is running
  and finished values do not exist.

The reference resolver short-circuits the terminal state rather than
approaching it, so no accumulation of rounding can leave a price at `0.9999`
opacity or a card at `1.0001` scale.

## Motion tokens

`designSystem` gains a fourth catalog, `motions`, mirroring `colors`,
`backgrounds`, and `shadows` exactly. It is **required** and may be empty.

```json
{
  "designSystem": {
    "colors": [],
    "backgrounds": [],
    "shadows": [],
    "motions": [
      {
        "id": "motion-entrance",
        "name": "Entrance",
        "value": { "type": "motion", "durationMilliseconds": 240, "easing": "decelerate" }
      },
      {
        "id": "motion-entrance-alias",
        "name": "Entrance alias",
        "value": { "type": "motionToken", "id": "motion-entrance" }
      }
    ]
  }
}
```

A motion is referenced as `{ "type": "motionToken", "id": "motion-entrance" }`
or authored inline as `{ "type": "motion", "durationMilliseconds": …,
"easing": … }`, mirroring the `inlineShadow` / `shadowTokenReference` pair.

Duration and easing are **one composite** because neither is meaningful
without the other: a duration with no curve and a curve with no duration are
both half a decision. Durations are **integers**, `0…2000`, following the
`0.3` doctrine that Dart, Swift, Kotlin, and JavaScript must not disagree
about a rounded fraction. `0` is legal and means the change applies instantly.

IDs and display names are unique inside the catalog, token-to-token references
are permitted, every reference must resolve, and the graph must be acyclic —
the same rules the other three catalogs carry.

### Unused motion tokens are rejected; unused colours are not

This is a **deliberate asymmetry**, called out here so that nobody later
"fixes" the colour, background, and shadow catalogs to match it.

An unreferenced colour token is inert. Its only risk is being wrong, and being
wrong about a colour nothing draws costs nothing.

An unreferenced **motion** token is different, because the safety constraint on
a motion lives at its **reference site**, not at its declaration. The
flash-safety floor is checked where a `loop` names a curve. A motion token that
nothing references has therefore never been checked against anything, and it
sits in the catalog looking like an approved timing value. The next author to
reach for it inherits a duration that no rule has ever seen. That is a latent
accessibility decision, not an inert value, so the validator rejects it.

**Used means reachable from a node.** The reference sites that make a token
used are the `motion` blocks on nodes, and usage propagates from there: a token
reached through another **used** token is used, and a token reached only through
an **unused** one is not. Both are then reported, one error per token, so the
catalog entry an author would reach for next is named rather than left implied.

> **Narrowing correction, 2026-08-11.** Every implementation of this rule walked
> `designSystem` itself as a reference root, which let a token vouch for the
> token it names: an orphan pair `a → b`, referenced by no node, reported only
> `a`. The verdict was never wrong — such a document was always rejected — but
> the diagnosis was half-complete, and the transitive-reachability branch
> underneath was consequently unreachable code. The reference implementations
> (`protocol/tools/validation-v0.4.mjs` and `protocol/browser/index.js`) now
> root usage at node reference sites only and compute reachability from there.
> `fixtures/v0.4/invalid/unused-token-transitive.json` pins the corrected
> diagnosis. The Go, Flutter, iOS, and Android mirrors are being corrected in
> parallel against that fixture.

Unknown references are checked everywhere, not only on nodes: a `motionToken`
inside another token's value must still resolve. Only the *usage* question is
rooted at nodes.

## Easing: four presets, and the reason there are only four

`easing` is one of `linear`, `standard`, `decelerate`, `accelerate`. The
control points are **normative** and fixture-pinned:

| Preset | Cubic-bezier control points | Use |
| --- | --- | --- |
| `linear` | `0, 0, 1, 1` | no shaping; `y = x` exactly |
| `standard` | `0.4, 0, 0.2, 1` | movement that starts and ends on screen |
| `decelerate` | `0, 0, 0.2, 1` | something entering; fast in, settles |
| `accelerate` | `0.4, 0, 1, 1` | something leaving; slow out, speeds up |

These map exactly onto SwiftUI `timingCurve(_:_:_:_:)`, Compose
`CubicBezierEasing`, and Flutter `Cubic`, which is the whole reason for
choosing cubic beziers: it is the one faithfully portable curve family across
the three renderers.

**Springs are excluded.** They have three different parameterizations and
three different settling rules across the supported platforms, and matching
them across renderers means reimplementing the ODE and then fighting each
platform's own implementation.

**Authored control points are excluded.** An out-of-range `y` fakes a spring,
and overshoot is exactly where the three platforms clamp opacity and scale
differently. Every preset above is monotonic and stays within `0…1`; a test
asserts it. Widening to authored curves later is cheap. Retracting them would
not be.

## Three primitives, constrained by trigger

A node may carry a `motion` block. Which members it may carry depends on what
the node is:

| Trigger | Allowed on | Document-rejecting rule |
| --- | --- | --- |
| `appear` | any node except the screen Scroll Container | a node with `appear` may not descend from another node with `appear` |
| `selection` | `productSelector`, `tabs` | — |
| `loop` | `button` | at most one per **screen** |

The screen Scroll Container is excluded for the same reason `0.3` excludes it
from `sizing`: it is viewport-owned rather than authored.

### `appear`

```json
{
  "motion": {
    "appear": {
      "effect": "fadeRise",
      "riseLogicalSize": 12,
      "curve": { "type": "motionToken", "id": "motion-entrance" },
      "delayMilliseconds": 80
    }
  }
}
```

Plays once when the node first enters a screen. `effect` is `fade` or
`fadeRise`; `riseLogicalSize` is **required with `fadeRise` and forbidden with
`fade`**, enforced by the schema rather than by prose. It is bounded at `64`
logical units: a rise longer than the component it moves reads as a fly-in
rather than an entrance, and a large authored translation is where
transform-versus-layout divergence between three renderers becomes visible.
The node travels *to* its laid-out position, so its final geometry is its
static geometry.

`delayMilliseconds` is how stagger is authored. Siblings with `0`, `80`, and
`160` produce a staggered reveal. There is **no stagger sugar** in `0.4` — see
[deferrals](#explicit-deferrals).

**Nested `appear` rejects the document.** Two entrance opacities multiply, and
the three renderers compose that product at different points in their
pipelines: rejecting is cheaper than pinning an arithmetic that no platform
agrees on, and an author who wants a group to fade in puts the `appear` on the
group.

#### Product Card internals may carry `appear`

`appear` is allowed on `productCard`, `productBadge`, and the Product Card
passive stack (`$defs.productCardPassiveStack`), and this is **deliberate
rather than incidental**. The schema has said so since the `0.4` draft landed —
all three carry `nodeMotion` — but the prose never confirmed it, and a
permission that only the schema states is one every renderer team has to guess
at.

Staggering the cards of a Product Selector is the clearest use of
`delayMilliseconds` in the whole contract: three plans revealing at `0`, `80`,
and `160` is the effect authors reach for first, and forbidding it would push
them to animate the Selector as one block, which is a worse design for the same
authoring effort.

Three existing rules already constrain it, and none of them needed changing:

- **The nesting rule applies unchanged.** A `productCard` with `appear` inside
  a `productSelector` with `appear` is rejected, as is a passive stack with
  `appear` inside a `productCard` that has one. Authors stagger at exactly one
  level of the card tree.
- **`appear` is entry-scoped, not selection-scoped.** It plays once when the
  node first enters the screen. Selecting a different plan is a *selection*
  change and must not replay a card's entrance — `selection` motion is the
  primitive for that, and it lives on the Selector. A renderer that keys its
  entrance off card re-composition rather than off screen entry will replay
  entrances on every tap; that is an implementation bug, not authored
  behaviour.
- **The terminal-state rule applies unchanged**, so a mid-entrance card is
  already present, focusable, announceable, and selectable. An entrance can
  never make a price or a plan unreachable.

`selection` and `loop` remain unavailable here: `selection` is allowed only on
the two components that own runtime selection state, and `loop` only on Button.

### `selection`

```json
{ "motion": { "selection": { "curve": { "type": "motionToken", "id": "motion-selection" } } } }
```

Interpolates the authored Default and Selected box styles when the runtime
selection changes. Allowed only on the two components that own runtime
selection state.

The interpolable field list is **closed**:

| Field | Behaviour |
| --- | --- |
| `background` | interpolates when both endpoints are `{"type":"color"}` with canonical `#RRGGBBAA` literals; otherwise switches at `t = 0.5` |
| `border.color` | as above |
| `border.width`, `cornerRadius`, `opacity` | always interpolate |
| `shadow` | interpolates when both endpoints are inline shadows; colour follows the colour rule |
| `background` *kind* change, `padding` | **switch discretely at `t = 0.5`** |

A semantic colour name resolves against the renderer's theme and a
`colorToken` resolves against the document; neither has a numeric value the
protocol can average, so rather than invent one, the change applies at the
half-way point. Padding is structural: interpolating it relayouts the subtree
every frame on three layout engines that disagree about when that is legal.

Tabs `selection` animates the **tab control's style, not the panel swap**.
`0.3` visibility semantics remove a hidden node from layout, the accessibility
tree, and focus order; animating a removal would require a "present but not
focusable" third state that does not exist. Exit animation is later work.

### `loop`

```json
{
  "motion": {
    "loop": {
      "effect": "pulse",
      "scaleAmplitude": 0.04,
      "opacityAmplitude": 0.12,
      "curve": { "type": "motionToken", "id": "motion-pulse" },
      "repeat": { "count": 3 }
    }
  }
}
```

A bounded call-to-action pulse. One cycle is an excursion out and back: scale
runs `1 → 1 + scaleAmplitude → 1`, opacity runs `O → O × (1 −
opacityAmplitude) → O`, both driven by the same eased phase, peaking at the
half-cycle. The excursion is `0` at **both ends of every cycle**, so a cycle
boundary is the static rendering rather than a near miss.

**`repeat.count` is `1…5`. There is no `forever` mode anywhere in the
schema.** This is an owner ruling on accessibility grounds. An unbounded pulse
would rely on the operating system's reduce-motion switch as its WCAG 2.2.2
stop mechanism, which means a user who has not enabled that switch has no stop
mechanism at all. A bounded count needs no stop control because it stops.

#### Time origin: node entry

> **Ruling.** A `loop`'s elapsed clock starts when the node **enters the
> screen** — the same origin as `appear`, and the same origin whether or not
> the node carries an `appear` at all. It does not wait for an entrance to
> finish.

`buttonMotion` permits `appear` and `loop` on one Button, so a Button can be
entering and pulsing at once and the two clocks have to be related by
something. The frame vectors cannot answer this: `resolveV04MotionFrame` takes
one `trigger` and one `elapsedMilliseconds`, so it describes each trigger in
isolation and is silent about what `t = 0` is measured from. That silence is
what this ruling closes.

**One origin per node** is the whole reason for the choice. The alternative —
start the pulse when the entrance completes — makes one trigger's origin a
function of another trigger's `delayMilliseconds` plus its resolved curve
duration, which means a renderer cannot drive a `loop` without first resolving
an `appear` it may not have. That is a coupling between two independently
specified primitives, and it is exactly the kind of cross-trigger arithmetic
three renderers get subtly different. Node entry is a single event all three
platforms already observe, because `appear` needs it.

The terminal state is unaffected either way, which is why this is a
coordination choice rather than a correctness one: a bounded pulse rests at
excursion `0` and an entrance ends at its laid-out position, so both orderings
converge on the same static rendering.

When the two do overlap, they compose on the node's own values:

```text
opacity = resolvedStaticOpacity × appearProgress × loopOpacityMultiplier
scale   = loopScale
```

This is **not** the nested-`appear` case and does not reopen it. Nested
`appear` is rejected because two *different nodes* in an ancestor chain each
apply an entrance opacity, and the three renderers compose that product at
different points in their pipelines. Here both factors belong to one node and
are applied at one place in one node's own rendering, which every platform can
express identically. `appear` additionally contributes a translation and
`loop` a scale; the translation is the entrance's and the scale is the pulse's,
and neither reads the other.

Authors who want the pulse to begin after the entrance already have the
mechanism: give the `loop` curve a longer duration, or accept that the first
cycle overlaps a 240 ms entrance — at a `scaleAmplitude` ceiling of `0.06` the
overlap is not perceptible as a separate effect.

All three renderers already implement node entry, each by starting the two
clocks in one mount: Compose launches both elapsed clocks in the same
composition (`MosaicPaywallMotion.kt`), SwiftUI stamps the loop's `startedAt`
in the same `onAppear` that begins the entrance
(`PaywallRendererMotion.swift`), and Flutter starts both timelines in the same
`initState` pass (`renderer_motion.dart`). This ruling therefore records
existing behaviour rather than asking for a change.

**It is now protected by a test on all three SDKs.** Each suite drives one
Button carrying both an `appear` and a `loop` and asserts that the pulse clock
runs from node entry while the entrance is still in flight, against the
composition formula above: Flutter in `9ecf70e`, iOS in `a79ffb2`, Android in
`7b3f64d`. The protocol still supplies no vector for the combined case —
`resolveV04MotionFrame` takes one trigger per call by design, and widening it to
accept a trigger *set* would be a contract change rather than a clarification —
so the formula above remains the specification those renderer tests assert
against.

#### Opacity floor semantics

`opacityAmplitude` is a **fraction of the node's resolved static opacity**, not
an absolute value. The floor is `resolvedOpacity × (1 − opacityAmplitude)` and
the rest value is `resolvedOpacity` exactly.

This matters twice. It keeps the terminal-state rule exact for a node that
authored `appearance.opacity: 0.8` — the pulse rests at `0.8`, not at `1.0`.
And it means the pulse can never drive a price fainter than the author asked
for: the ceiling of `0.2` puts the floor at no less than 80% of whatever the
static rendering already was.

`opacityAmplitude` may be `0`, which is a pulse that scales without dimming.
`scaleAmplitude` must be positive: a pulse that does not scale is not a pulse.

## Replay on screen re-entry

> **Ruling, 2026-08-11.** `appear` and `loop` **replay on genuine screen
> re-entry**. Each user-initiated navigation entry is a fresh viewing context,
> so a node entering a screen for the second time animates exactly as it did the
> first. `repeat.count` is therefore a bound **per screen entry**, not per
> session: a `count: 3` pulse runs three cycles each time the user arrives, not
> three times ever.

The [time origin](#time-origin-node-entry) ruling fixed `t = 0` at node entry
and left open how many times that origin can occur. This closes it.

**What counts as an entry.** A **Screen-to-Screen navigation** — the surface
actually leaving and later returning. A rebuild *within* one entry is not a new
entry: toggling a Switch, changing a Tabs selection, selecting a different
Product Card, or re-laying out after a size change all leave the node in the
same viewing context, and nothing replays. The distinction is whether the
surface left, not the renderer's render count.

### Sheets are not re-entries

> **Ruling, 2026-08-11.** Presenting a Sheet **does not leave the screen
> beneath** — that screen remains presented, underneath. Neither opening nor
> dismissing a Sheet is therefore an entry of the screen beneath it: its
> entrances do not replay, and its pulse budget does not reset. Only a
> Screen-to-Screen navigation is an entry. A Sheet's *own* content enters when
> the Sheet is presented, and re-entering a Sheet is an entry of the Sheet.

This settles a live three-way divergence. Flutter treated `navigateBack` from a
Sheet as re-entering the screen beneath and replayed its motion; iOS and Android
pinned the opposite. Nothing in the contract said which was right, so all three
were equally defensible readings of "entry".

The rationale is that this is **not a new rule** — it is the existing sheet
contract applied to motion. `0.3` already specifies that a Sheet is presented
*over* its screen and that the screen behind a sheet never left: that is why the
customer's scroll position, Switch and Tabs selections, Carousel page, and
Product Card selection all survive a sheet round trip untouched. Motion has to
agree with the rest of the runtime state. A screen whose selections demonstrably
persisted across a sheet, but whose entrances replayed, would be asserting two
different answers to the same question about whether the customer left.

The consequences follow directly and are the reason this matters more than it
first appears:

- **The pulse budget cannot be farmed.** If a sheet round trip were an entry, a
  `count: 3` pulse would be handed three fresh cycles every time the customer
  opened and closed a disclosure sheet — and a "read the terms" sheet is exactly
  the thing a paywall invites them to open. The bound would then be defeated by
  ordinary use rather than by an author doing anything unusual, which is the one
  outcome [ruling 2](../architecture/decisions/0027-protocol-0.4-motion.md) was
  written to prevent.
- **A disclosure sheet cannot be turned into a motion trigger.** Re-animating a
  paywall each time a customer closes the legal text would make the terms link
  an animation control, which is not what the author authored.

All three renderers now pin this ruling. iOS and Android already did; Flutter's
sheet-dismissal path returned to the screen beneath without recording an entry
as of `63474fe`, and both its `navigateBack` and its customer-dragged dismissal
take that path. Renderer tests must keep the sheet round trip as their
**negative** case alongside the screen round trip, because it is the half a
naive "the widget rebuilt, so replay" implementation gets wrong.

### Why this does not reopen WCAG 2.2.2

The bounded `repeat.count` exists because an unbounded pulse would depend on the
operating system's reduce-motion switch as its stop mechanism, leaving a user
who has not enabled that switch with no stop mechanism at all. Replay on
re-entry does not weaken that:

- **WCAG 2.2.2's subject is content that moves outside the user's control.**
  Motion re-triggered by the user's own navigation is user-initiated. The user
  arrived; the paywall responded. That is the same category as a control
  animating because it was tapped, not the category of content that starts
  moving on its own and does not stop.
- **The bound still holds where it is checked.** Within each viewing, the pulse
  runs a bounded number of cycles and stops without any stop control. The
  guarantee the ruling makes — *this motion ends on its own* — is a property of
  a viewing, and every viewing has it.
- **A per-session bound would be the weaker contract, not the stronger one.**
  It requires renderers to carry cross-screen motion history, which is state the
  protocol does not model, cannot express in a document, and cannot pin with a
  frame vector. Three renderers would each invent their own key for "have I
  played this yet", which is how divergence starts.

The terminal-state rule is untouched: a replayed entrance still ends
byte-identical to the static rendering, so re-entry can never leave a price or a
disclosure in a different place than a first entry did.

### The deliberate contrast with Local Preview

[Local Preview `0.4`](local-preview-v0.4.md#the-entrance-replay-suppression-rule)
does the opposite: `motion.playedAppearScreens` **suppresses** entrance replay
for screens that have already shown their entrance in the preview session.

That is not an inconsistency, because the two rules have different subjects.
Local Preview's replays are triggered by an **author** accepting a revision —
dozens of times a minute while nudging padding — and none of them is a viewing
the end user ever has. Suppression exists so a designer is not strobed once per
keystroke. This ruling's replays are triggered by an **end user** navigating,
which is the thing the paywall is supposed to respond to.

Stated as one line: **a new viewing replays; a new revision of the same viewing
does not.** Local Preview's rule is scoped to the preview session and does not
travel into the delivered contract, and this ruling is scoped to navigation and
does not weaken Local Preview's suppression.

### Implementation status

All three renderers already replay on re-entry, and each does so by the same
mechanism that gives them the node-entry time origin: the node leaves the
composition, view tree, or element tree when the screen does, and both clocks
restart in the mount that brings it back — Compose's `LaunchedEffect` in a fresh
composition (`MosaicPaywallMotion.kt`), SwiftUI's `onAppear` on a re-created view
(`PaywallRendererMotion.swift`), and Flutter's `initState` on a re-created state
object (`renderer_motion.dart`). This ruling records existing behaviour.

**It is not yet protected by a test.** No SDK navigates away from a screen and
back and asserts that the entrance and the pulse run again, so a refactor that
hoisted motion state above the screen — a plausible optimisation — would fail
nothing. Renderer tests pinning re-entry replay are a **required follow-up**,
owned by the renderer wave. The protocol cannot supply that vector:
`resolveV04MotionFrame` resolves one trigger at one elapsed time and knows
nothing about navigation, so what has to be asserted is that the elapsed clock
returns to `0`, which only a renderer can observe.

The protocol does supply the **document** those tests need.
`protocol/fixtures/v0.4/screen-round-trip.json` authors two
`screen`-presentation screens joined by `navigateTo` and `navigateBack`, each
carrying an entrance and a bounded loop, so a renderer can drive a genuine
screen round trip and assert that both restart. It exists because no other
canonical fixture can play that role: `navigation-only.json` has two screens and
no motion, and `complete-paywall.json` has motion on two surfaces of which the
second is a **sheet** — the case where nothing replays. A renderer testing only
against the canonical document therefore exercises the negative half of this
ruling and infers the positive half, which is precisely how the three-way
divergence above went unnoticed. Both halves now have a document: this fixture
for the screen round trip, and the canonical document's sheet for the case that
must not replay.

## Flash safety is schema- and validator-enforced, not advised

| Bound | Value | Why |
| --- | --- | --- |
| `loop` curve duration | ≥ **500 ms** | caps the pulse's fundamental at 2 Hz and its perceived rate at 1 Hz, an order of magnitude below the three-per-second threshold WCAG 2.3.1 draws |
| `scaleAmplitude` | ≤ **0.06** | a 6% excursion is noticeable and not startling; larger excursions overlap neighbouring content and change perceived hit targets |
| `opacityAmplitude` | ≤ **0.2** | keeps the floor at ≥ 80% of the static opacity, well clear of a flash |
| colour loops | **inexpressible** | a looping colour change *is* the flash primitive; `pulse` carries only scale and opacity, so it is excluded structurally rather than by a rule someone can argue with |
| `repeat.count` | ≤ **5** | bounded above by construction |

The duration floor is checked in the **semantic** layer rather than the schema
because the duration lives on a token and the constraint belongs to the
reference site: the same 240 ms token is legitimate for an entrance and
illegitimate for a pulse.

**Motion never touches the accessibility tree.** A node mid-entrance is already
present, focusable, and announceable; a pulsing button announces exactly what a
static one announces. There is no motion-conditional accessibility state and no
way to author one.

## The reduced-motion contract

This is **protocol-mandated**, not renderer-interpreted. The signal is
injected at the renderer boundary like the clock, so it is testable.

### Platform signal mapping

| Platform | Signal | Reduced motion when |
| --- | --- | --- |
| iOS / SwiftUI | `UIAccessibility.isReduceMotionEnabled` (`accessibilityReduceMotion`) | `true` |
| Android / Compose | `Settings.Global.ANIMATOR_DURATION_SCALE` | `0` |
| Flutter | `MediaQuery.disableAnimationsOf(context)` | `true` |
| Studio / web chrome | `prefers-reduced-motion: reduce` | matches |

### Per-primitive behaviour

| Primitive | Under reduced motion |
| --- | --- |
| `appear` | **opacity only.** The transform is dropped; `translateLogicalSize` is `0` at every instant, including the start frame. |
| `selection` | **applies instantly.** The frame at every elapsed time is the resolved Selected style exactly. |
| `loop` | **fully disabled.** The node sits at rest — scale `1`, opacity multiplier `1`, which is the static rendering. |

The `appear` ruling is what resolves the iOS-replace versus Android-remove
divergence without per-platform clauses: **the contract owns *what* changes and
the platform owns *how long*.** A renderer may shorten or zero the duration of
the remaining opacity change according to its platform's convention. What is
normative is that no transform occurs and that the terminal state is unchanged.

### Video backgrounds under reduced motion

> **Ruling.** `0.3` specifies video backgrounds as "always muted, autoplaying,
> looping, and control-free" and no SDK reads the platform reduced-motion
> signal. Apple's App Store Reduced Motion evaluation criteria cover "any other
> ongoing motion", so a Mosaic paywall can invalidate a customer's
> accessibility declaration. The owner ruled that this ships as **specified
> `0.4` behaviour**, not as a `0.3` defect patch. The live exposure remains
> open until `0.4` lands and is accepted.

**Under reduced motion, a video background does not play.** The renderer
renders the declared `posterAssetId` if that image is available, and otherwise
the declared `fallbackColor`. No frame of the video is shown, playback is not
started and paused, and no control is offered.

This is the same resolution order the existing `missingMediaBackground` policy
already uses, which is deliberate: the reduced-motion path reuses a path that
three renderers have already implemented rather than introducing a fourth
outcome. It is recorded machine-readably in the manifest as
`readerPolicy.reducedMotionVideoBackground:
"renderPosterThenFallbackColorWithoutPlayback"`.

**A platform-level media setting may also stop playback, on a document of any
version.** iOS's Video Autoplay switch is the example: it is a user preference
the platform owns, narrower than reduced motion and separate from it, and a
renderer must honour it wherever the host platform exposes one — including on a
`0.3` document, which this `0.4` ruling does not reach. The two are distinct in
kind: the rule above is a protocol obligation gated on `0.4`, while this is the
customer's own setting, which no contract version can override.

A video background authored with no `posterAssetId` degrades to its fallback
colour under reduced motion. Authors who care about that case declare a poster;
the protocol does not make one mandatory, because a colour is a legitimate
answer and a required-but-ignorable field is worse than an optional one.

**This ruling is implemented on all three renderers.** iOS gates playback on
`MotionAccessibility.permitsVideoPlayback` (`MotionDriver.swift`, consumed in
`PaywallRendererControls.swift`), Flutter resolves poster-then-fallback-colour
in `renderer_appearance.dart`, and Compose handles it explicitly in
`MosaicDecorativeVideoBackground` rather than letting the animation-scale
setting imply it. The live `0.3` exposure the ruling names closes when `0.4`
itself is accepted, not before.

## The enhancement tier

Every capability in every Mosaic contract before this one carries `fallback:
"rejectDocument"` as a schema `const`, and server-side stripping of material a
reader cannot understand is doctrine-forbidden. Motion introduces the first
exception.

Three capabilities — `motion.appear`, `motion.selection`, `motion.loop` —
carry **`renderWithoutMotion`**. Everything else still carries
`rejectDocument`, and a validator asserts that partition rather than trusting
review to notice a drift.

The value is named for **motion specifically**, not generically. A
`renderWithoutFeature` would be an invitation to relitigate the
no-partial-rendering doctrine once per feature; a motion-shaped name cannot
spread by imitation.

The reader policy splits accordingly:

```json
{
  "unsupportedRequiredCapability": "rejectDocument",
  "unsupportedEnhancementCapability": "renderStaticDocument"
}
```

A reader missing `component.tabs` still rejects the whole document. A reader
missing `motion.loop` renders the document **statically and completely** —
which the terminal-state rule guarantees is the full authored design.

Granularity is three capabilities rather than one, by the `0.3`
distinguishability test: a renderer that can cross-fade a selection but has no
per-node entrance driver is a real renderer, and one capability could not say
so. Capability derivation is unchanged in shape and needs no special case: a
`motion.*` capability is derived exactly when that motion occurs, and the
existing unused-capability rule actively protects the tier by rejecting a
document that claims motion it does not author.

## Conformance: the frame vectors

Motion is the first thing in the protocol whose contract is a *value at an
instant* rather than a value. Prose cannot pin that, and three renderers will
not agree by coincidence.

`protocol/fixtures/v0.4/motion-frames.json` records, for every trigger, effect,
and easing preset, the exact frame a renderer must be showing at `t = 0`, a
quarter, a half, three quarters, and the end — plus the reduced-motion answer
for each, an authored-delay case, and the per-cycle phases of the pulse.

- Generated by `resolveV04MotionFrame` in `protocol/tools/validation-v0.4.mjs`
  and reconciled against it by `npm run validate`. **The tool and the fixture
  cannot drift**: a hand edit to either fails the gate.
- Mirrored as `resolveMotionFrame` in `protocol/browser/index.js`, with a test
  that drives every frame of every case through both implementations.
- Numbers carry **four decimal places**. The stated tolerance is
  `toleranceAbsolute: 0.001` — continuous interpolation cannot be byte-pinned
  across three platform bezier solvers, and 1e-3 is two orders of magnitude
  below perceptibility.
- The last frame of every case is the terminal state, and the validator rejects
  a case that never reaches it.

```js
resolveV04MotionFrame(motion, {
  trigger,               // "appear" | "selection" | "loop"
  elapsedMilliseconds,   // whole, non-negative; throws otherwise
  reducedMotion,         // boolean
  resolvedFrom,          // selection only; required there, forbidden elsewhere
  resolvedTo,
});
```

The resolver is pure and integer-in, following the `resolveV03CountdownState`
precedent: a clock that cannot be trusted **throws** rather than resolving,
because arithmetic on a bad clock yields a frame that reads back as plausible.
The `curve` must already be resolved to an inline motion; a `motionToken`
reference throws, because a resolver that silently accepted an unresolvable
token would return the frame for a duration nobody authored.

**The vectors describe each trigger in isolation and do not fix a time
origin.** `elapsedMilliseconds` is measured from whatever the contract says
that trigger's origin is, and the resolver takes one trigger at a time, so no
vector can tell a renderer how two concurrent triggers on one node relate. That
is prose, not a vector: `appear` and `loop` both start at **node entry** (see
[Time origin](#time-origin-node-entry)), and `selection` starts at the
selection change. Two renderers can therefore agree on every committed vector
and still disagree on screen, which is the failure mode this note exists to
prevent.

Renderers additionally need an injectable **motion driver** — Compose
`mainClock.advanceTimeBy`, Flutter `tester.pump(duration)`, iOS driving
progress directly — and every existing static golden must be captured with the
driver disabled. Android's SHA-256 zero-tolerance goldens make that
non-optional rather than advisable. **All three drivers have landed**, each with
a conformance suite reading these vectors: `MotionDriver.swift` (`b1c5bbb`),
`motion_driver.dart` (`d0b2e2b`), and `MosaicPaywallMotion.kt` with a
recaptured `mosaic-paywall-v04-golden.sha256` (`ed02c07`).

## Bundled `0.3` cleanups

`0.3` flagged two items for this version. Both are applied here, because a
version bump has a fixed cost and paying it twice for two one-line cleanups is
worse than paying it once.

### `style.productCardStates` is removed

`0.3` records it as "a legacy co-derived signal": it is derived exactly when
`component.productSelector`, `component.productCard`, or
`component.productBadge` is derived, because `styles` is required on all three.
A capability that can never vary independently of another capability carries no
information. `0.3` kept it only to avoid churning four teams mid-implementation
and named it for removal here.

It is gone from the schema enum, the manifest, and the derivation. A `0.4`
document that declares it is rejected as an unknown capability.

### One marker vocabulary

`0.3` notes that Feature List's `marker` is the single constant `"checkmark"`,
so a list cannot express a **negated** item — "not included" on a comparison
paywall — and that Timeline's three-arm marker union is the shape Feature List
would adopt, with the two idioms in one protocol being "a known and visible
asymmetry, and a candidate for consolidation in `0.4`".

`0.4` consolidates. One shared `marker` union — `{"kind":"dot"}`,
`{"kind":"ordinal"}`, `{"kind":"icon","name":<iconName>}` — is used by both
components. Feature List's component-level `marker` is the list's default
glyph, and an **item** may override it:

```json
{
  "type": "featureList",
  "marker": { "kind": "icon", "name": "checkmark" },
  "markerColor": "action.primary",
  "items": [
    { "id": "unlimited-projects", "text": { "…": "…" } },
    { "id": "priority-support", "marker": { "kind": "icon", "name": "close" }, "text": { "…": "…" } }
  ]
}
```

An absent item `marker` means the item carries the list's marker. It is never a
request for no glyph.

Marker **colour and size stay component-level**, exactly as they are on
Timeline. A per-item marker colour — a green tick beside a red cross — is a
second axis and a deliberate deferral, not an oversight: the negated case is
carried by the glyph, and adding a per-item colour without a per-item size
would be a half-measure that the next redesign has to undo.

#### `markerSize`, and what its absence means

> **Ruling, 2026-08-11.** `featureListComponent.markerSize` is a
> `positiveLogicalSize`, bounded exactly as Timeline's field of the same name.
> It is **optional**, and **absent means the list's own `typography.fontSize`**.
> A renderer must not substitute a size of its own.

`0.4` shipped `markerColor` without a `markerSize`, and the sentence above was
therefore not true: size did not stay component-level, because it did not exist.
Each renderer supplied its own answer — Flutter drew a fixed `20`, Compose
derived the list's font size — which is a visible cross-platform divergence in
the one component every paywall uses.

The field is **optional rather than required**, which is the one place it
departs from Timeline. Timeline's `markerColor` and `markerSize` are required
exactly when an entry declares a marker and forbidden when none does, because a
Timeline marker is optional and there is genuinely nothing to size when it is
absent. A Feature List always declares a marker, so there is always something to
size and always a value to fall back on. Requiring it would additionally
invalidate every document already authored against `0.4` and add a step to a
migration whose whole claim is that it changes nothing else, in exchange for a
value the protocol can state once.

The default follows Timeline's precedent for absent values: **fall back to
another authored value on the same component, never to a constant.** Timeline's
marker gutter is `markerSize` wide when an entry declares a marker and
`connector.width` wide when none does — a sibling authored value, not a magic
number. `typography.fontSize` is the Feature List's equivalent: it is required
on the component, so the default always resolves; it is what a glyph sitting
beside a line of text should track; and a marker that does not track its line
scales wrongly under a large system font scale. Flutter's `20` is exactly the
kind of renderer-chosen constant this rule exists to remove.

What is *not* allowed is a renderer inventing a third answer. The absent case
has one normative value, so `markerSize` never becomes a masked default in the
sense `0.3` warns about: the value is specified, and only its authoring is
optional.

`markerColor` stays **required** and is not given a default in this pass.
Deriving it from `typography.color` would be a separate narrowing of a field
`0.4` inherited unchanged from `0.3`, and a marker colour is an accent chosen
*against* the text colour rather than a value tracking it.

The canonical fixture authors `markerSize: 18` against a `fontSize` of `16`, so
the authored and defaulted branches are distinguishable; `hidden-purchase-target`
leaves it absent, which exercises the default. A validator floor rejects a
canonical fixture that stops exercising the authored branch.

**This is the one `0.4` feature with no `0.3` representation.** `0.3`'s Feature
List marker is the single `const "checkmark"` and its items carry no marker
field, so a list using `dot`, `ordinal`, a non-checkmark icon, or any per-item
override cannot be projected back. Motion can be dropped losslessly; a negated
item cannot. See [the projectability
rule](#the-projectability-rule) — a document using the wider vocabulary is
simply not offered to `0.3` readers.

## Migration from `0.3`

The migration is mechanical. `protocol/fixtures/v0.4/` was produced from
`protocol/fixtures/v0.3/` by exactly these steps, applied by a script, so that
"mechanical" is a demonstrated property rather than a claim.

1. `schemaVersion`: `"0.3"` → `"0.4"`.
2. Every entry in `compatibility.requiredCapabilities`: `version` `"0.3"` →
   `"0.4"`.
3. **Remove** any `{"name": "style.productCardStates"}` entry.
4. Add `"motions": []` to `designSystem`. The catalog is required and may be
   empty.
5. Every Feature List: `"marker": "checkmark"` → `"marker": {"kind": "icon",
   "name": "checkmark"}`.

Nothing else changes. A `0.3` document that has been through those five steps
is a valid `0.4` document with no motion, and renders identically.

`markerSize` adds no sixth step. It is optional, and its absent value —
the list's own `typography.fontSize` — is exactly what a migrated `0.3` document
carries, so a migrated document authors nothing new and the migration stays a
rewrite rather than a decision.

Motion is then **purely additive**: adding a `motions` catalog and `motion`
blocks changes no static rendering, because of the terminal-state rule.

`0.4` does **not** read `0.3` documents and `0.3` does not read `0.4`
documents. Versions are exact identifiers; a reader declaring `0.4` accepts
only `0.4`. When `0.4` becomes deliverable, publishing may emit a `0.3`
representation by projection at publish time — the established Configuration
Delivery pattern — so that one authored document can serve both reader
generations.

### The projection is partial, not lossless

An earlier draft of this document called that projection lossless. It is not,
and the claim was wrong because it considered only motion.

**Motion projects losslessly.** Dropping `motion` blocks and the `motions`
catalog changes no rendering, for exactly the same reason `renderWithoutMotion`
is lossless: the terminal state of every animation is byte-identical to the
static rendering, so the thing a `0.3` reader draws is the thing a `0.4` reader
ends at.

**The bundled marker consolidation does not.** `0.3`'s
`featureListComponent.marker` is the single `const "checkmark"`, and `0.3`'s
`featureListItem` declares only `id` and `text` under
`additionalProperties: false`. So `0.3` has **no representation at all** for:

- a Feature List whose `marker` is `{"kind":"dot"}` or `{"kind":"ordinal"}`;
- a Feature List whose `marker` is an icon other than `checkmark`; or
- **any** per-item `marker` override — including the negated "not included"
  item that the consolidation exists to make expressible.

There is no substitute to fall back to. Projecting a negated item as a
checkmark inverts the meaning of a comparison paywall: it would tell a `0.3`
reader that an excluded feature is included. Dropping the item hides a
disclosure. Both are worse than not shipping a `0.3` representation.

Timeline is unaffected. Its three-arm marker union is byte-identical in the two
versions, so a `0.4` Timeline marker projects unchanged. The loss is confined
to Feature List.

### The projectability rule

> **Normative.** A `0.4` document is **`0.3`-projectable** only if every Feature
> List in it carries `marker: {"kind":"icon","name":"checkmark"}` and no Feature
> List **item** carries a `marker`. A `0.4` document that is not
> `0.3`-projectable has no `0.3` representation, and one must not be
> manufactured.

Publishing must therefore perform a **projectability check** and, when it
fails, **decline to emit the `0.3` representation** rather than emit a corrupt
one. This is the `safeV1Projection` precedent in
`apps/api/internal/hostedpublishing/service_publish.go`: a projection that
cannot be constructed faithfully is simply not constructed, and the release
carries only the representations it can honestly carry.

Graceful non-emission is not a new failure mode for readers. A `0.3`-only
reader that requests a release with no `0.3` representation is refused through
the **existing `rejectDocument` flow** — the same path it already takes for any
capability it does not support. It receives no paywall rather than a wrong one,
which is what every other unsupported-capability refusal in the protocol
already does.

Note that this is the opposite direction from the enhancement tier, and
deliberately so. `renderWithoutMotion` lets a reader that is missing a
capability still see the complete authored design, because motion has a
provably equivalent static form. A non-checkmark marker has no equivalent form
in `0.3` at all, so there is nothing to degrade *to*, and refusal is the only
honest answer.

Authors who need one document to serve both reader generations keep their
Feature Lists on the checkmark marker. That constraint is a publishing-time
property of a document, not a schema restriction: `0.4` authoring is
unrestricted, and the cost of using the wider vocabulary is the loss of the
`0.3` audience for that release.

Renderer and backend implementation of this rule is a later wave; the backend
integration point is flagged in [what has since
landed](#what-this-slice-did-not-include-and-what-has-since-landed). That
deferral remains accurate: no publish path performs a projectability check
today.

### Configuration Delivery cannot yet carry `0.4`

A related and separately tracked gap, recorded here because the projectability
rule is otherwise easy to mistake for the only thing standing between a `0.4`
document and a device.

Configuration Delivery **v1, v2, and v3 all pin `0.3` structurally**, not by
convention:

- `paywallVersion.protocolVersion` is `const "0.3"` and
  `paywallVersion.document` `$ref`s `urn:mosaic:protocol:schema:v0.3:paywall`
  (defined once in v1's release schema and reused by v2 and v3);
- `protocolCompatibility.version` is `const "0.3"` in all three release schemas
  and in all three compatibility manifests; and
- v1's capability-request schema pins `"0.3"` on both sides of the negotiation.

So a `0.4` document has no hosted delivery representation at all: it cannot be
placed in a release, and an SDK cannot ask for one. Local Preview `0.4` is
currently the only transport that carries a `0.4` document end to end, which is
why the renderer work could land ahead of any delivery change.

Closing this is a **new Configuration Delivery version**, not an edit: v1, v2,
and v3 are released contracts, and widening a `const` in place would silently
change what an existing reader accepts. It is deferred rather than scheduled
here, because the version it belongs to depends on whether `0.4` is accepted as
drafted. Until then, `0.4` remains a draft that nothing produces or consumes in
production — which is exactly what [Status and
authority](#status-and-authority) claims, and this is the mechanism that makes
that claim true rather than aspirational.

## What `0.4` does not change

The announcement contract, the rating scale and its reserved localization keys,
locale resolution, product templates, visibility semantics, navigation, and
every `0.3` component are unchanged. The `0.4` accessibility-announcement
corpus travels with the canonical document because it names components by ID,
but it is reconciled against the **`0.3` reference implementation** rather than
a `0.4` copy of it: two implementations of one unchanged contract is exactly
the drift this repository has been bitten by before. The rating-announcement
and locale-resolution corpora are standalone and are not duplicated for the
same reason.

## Explicit exclusions, with reasons

These are excluded from the contract, not merely absent from it.

| Excluded | Reason |
| --- | --- |
| **Lottie / Rive** | a state machine is remote executable behaviour, a direct violation of the no-executable-code-in-remote-configuration rule; plus three native runtime dependencies and content no validator can inspect |
| **Keyframe timelines** | a mini animation language, which is the thing a declarative protocol exists to avoid |
| **Scroll-linked motion, parallax** | needs a scroll-state binding the protocol deliberately does not expose, and platform scroll physics differ by construction. There are consequently no "parallax limits" to specify: there is no parallax |
| **Springs** | three parameterizations, three settling rules; matching them means reimplementing the ODE and fighting each platform's own |
| **Authored cubic-bezier control points** | out-of-range `y` fakes a spring, and overshoot is where platform clamping of opacity and scale diverges |
| **Screen and sheet transitions** | platform-owned; the same boundary `0.3` drew for focus order |
| **Shimmer** | moving gradient masks are where cross-platform fidelity dies, and on a CTA a shimmer reads as skeleton-loading |
| **Colour loops** | a looping colour change *is* the flash primitive; excluded structurally by `pulse` carrying only scale and opacity |
| **Countdown-conditional motion** | deferred: it adds a second time axis to conformance. Authored *urgency* motion is additionally a store-policy risk under Apple's fake-urgency guidance and Google Play's deceptive-behaviour policy, and the recommendation is permanent exclusion rather than deferral |

## Explicit deferrals

Deferred means "not now", not "never". Each needs a reviewed protocol change.

- **Exit and removal animation.** Requires a "present but not focusable" third
  visibility state that does not exist. `0.5` at the earliest.
- **Stagger sugar.** `0.4` has authored `delayMilliseconds` and nothing else.
  A `stagger` property on a container is convenience over a mechanism that
  already works, and it is easy to add once real documents show what the
  common shape is.
- **Carousel auto-advance.** A component behaviour rather than a motion
  primitive. If it is ever built it needs a pause affordance per WCAG 2.2.2.
- **Authored cubic-bezier control points.** Presets are cheap to widen and
  impossible to retract; the decision is reversible in this direction only.
- **Per-item Feature List marker colour and size.** Component-level
  `markerColor` and `markerSize` both exist; only the per-item axis is deferred.
- **A Configuration Delivery version that can carry a `0.4` document.** All
  three delivery versions pin `0.3` structurally; see [Configuration Delivery
  cannot yet carry `0.4`](#configuration-delivery-cannot-yet-carry-04).
- **Locale-aware numerals** in reserved accessibility strings, carried forward
  from `0.3`.
- **Horizontal Timeline orientation**, carried forward from `0.3`.

## Local Preview 0.4 has landed

Local Preview `0.3` is version-locked to Paywall Protocol `0.3` — its message
schema `$ref`s `urn:mosaic:protocol:schema:v0.3:paywall` directly — so a
paywall version bump does mandate a Local Preview bump. That mirror is now
built. Local Preview `0.3` is unchanged and still correct for `0.3` drafts.

All seven items this section originally enumerated are delivered; see
[Local Preview 0.4](local-preview-v0.4.md) for the contract.

1. `protocol/schema/local-preview/v0.4/` — `preview-message.schema.json`
   (`$ref` retargeted to `urn:mosaic:protocol:schema:v0.4:paywall`, `$id` and
   `previewProtocolVersion` bumped), `local-project.schema.json`, and
   `compatibility-manifest.schema.json`.
2. `protocol/compatibility/local-preview/v0.4.json`, `status: "draft"`.
3. The **runtime-state motion member**: the accepted-revision runtime state
   gains `motion: { "playedAppearScreens": [] }`, and Local Preview suppresses
   entrance replay on an accepted revision so that a designer nudging padding
   is not strobed once per keystroke.
4. `protocol/fixtures/local-preview/v0.4/` — `local-project.json`,
   `session-flow.messages.json`, and `accepted-revision-runtime-reset.json`
   updated with the new member.
5. `protocol/tools/preview-validation-v0.4.mjs` and its wiring into
   `validate.mjs`.
6. The WebSocket subprotocol `mosaic.local-preview.v0.4` in
   `browser/index.js` negotiation, with `0.4` added to
   `localPreviewVersionPreference` ahead of `0.3`.
7. `docs/protocol/local-preview-v0.4.md` and a `versioning.md` update.

Two things the checklist did not anticipate, both recorded here because the next
reader will otherwise re-derive them:

- **`playedAppearScreens: []` is the value of a *first* acceptance, not of
  every acceptance.** Written as a reset value it contradicts the suppression
  rule it sits beside: a member that resets to empty on every acceptance
  replays every entrance on every keystroke, which is the exact defect the rule
  exists to prevent. It is the one runtime member an acceptance carries
  forward, filtered through the accepted document's screens. The fixture pins
  all three states — before, after, and first — rather than the two `0.3`
  pinned.
- **Item 6 is not self-contained.** Negotiating `0.4` without also making
  `decideLocalPreviewDraftDelivery` version-aware yields a relay that agrees on
  a subprotocol and then withholds every draft on it, because the preview
  capability check was pinned to the literal `"0.3"`. The delivery decision and
  the message/local-project readers dispatch on version too.

### What Local Preview 0.4 does not include

The three native preview clients and Studio's preview surface are later waves.
This slice is the contract, its fixtures, its validator, and the browser
runtime that Studio builds on.
