# Mosaic protocol fixture lifecycle

Fixtures are the executable definition of a Mosaic contract. Prose describes
intent; fixtures are what every SDK, Studio, and the backend actually agree on.
A rule with no fixture is not enforced.

## Coverage obligation

Per `docs/architecture/conventions/protocol.md`, every meaningful protocol
feature requires fixtures covering: standard rendering, invalid values, long
text, RTL, accessibility scaling, missing assets, unavailable products,
unsupported components, and offline fallback.

## Layout

```text
protocol/fixtures/<contract>/<version>/
├── <valid-fixture>.json          # canonical valid documents
├── batches/ responses/           # contract-specific groupings
└── invalid/
    ├── <invalid-fixture>.json    # documents that must be rejected
    └── rejection-layers.json     # generated metadata (not a fixture)
```

## Adding a fixture

1. Name it for the behaviour it protects, not the mechanism —
   `incomplete-rollout-attribution.json`, not `test-case-4.json`. The filename is
   the failure message a future reader sees.
2. Put valid documents at the version root; documents that must be rejected in
   `invalid/`.
3. Make it **minimal and single-purpose.** An invalid fixture should violate
   exactly one rule. A fixture violating three rules still passes after two of
   them regress.
4. Reference it from the contract's compatibility manifest where the manifest
   declares canonical fixtures.
5. Run `npm --prefix protocol run generate && npm --prefix protocol run validate
   && npm --prefix protocol test`. Generation must produce zero drift.
6. If the fixture is consumed by SDKs, confirm every SDK either consumes it or
   has a declared reason not to.

Invalid fixtures are asserted to be rejected. A fixture that every layer accepts
fails validation with "was accepted", which is the intended safety net: it is
impossible to add an invalid fixture that quietly proves nothing.

## Freezing a fixture

A fixture referenced by an **approved** contract is frozen with that contract.
Its bytes are part of the immutable contract, because SDK conformance tests
assert against them and a change would silently change what conformance means.

Permitted on a frozen fixture: nothing that changes its parsed content.
Formatting is already canonical (2-space indent, trailing newline) and enforced.

Needed changes to a frozen fixture mean one of:

- **a new fixture** alongside it, if the old one is still a valid case; or
- **a new contract version**, if the change reflects a behaviour change.

## Retiring a fixture

Fixtures are retired only with the contract version they belong to, and
**retired fixtures stay in the repository permanently** — see the
[deprecation policy](deprecation-policy.md#what-retirement-does-and-does-not-do).
They are the only executable record of what a retired version meant.

A fixture is deleted only if it was never part of an approved contract and is
genuinely redundant. Deleting a fixture from an approved contract is a breaking
change to the conformance suite.

## Rejection-layer metadata

### Why it exists

Mosaic rejects invalid documents at two layers: the **canonical JSON Schema**,
and a **semantic validator** for rules JSON Schema cannot express — digest
coverage, reference resolution, graph cycles, cross-field arithmetic, byte-size
limits. An `invalid/` directory mixes both freely, which hid two things:

1. **What an SDK actually proves.** An SDK that "handles" an invalid fixture may
   be exercising its schema decoder, or may be relying on a semantic rule it
   never implemented. Without knowing the layer, a passing conformance test can
   mean either.
2. **Whether a narrowing moved a fixture between layers.** That movement is
   precisely what the [narrowing
   doctrine](breaking-change-process.md#the-narrowing-pre-approval-doctrine)
   permits and requires evidence for.

Fixtures are **not** moved between directories to express this. Moving files
would break every SDK path reference and rewrite history for a fact that is an
observation about current schemas, not a property of the fixture. The
classification is recorded as metadata instead.

### Format

Each `invalid/` directory contains a generated `rejection-layers.json`:

```json
{
  "contract": "Analytics Event v1",
  "description": "Generated by tools/generate-rejection-layers.mjs. ...",
  "layers": {
    "incomplete-rollout-attribution.json": "schema",
    "placement-request-unrelated-attribution.json": "schema",
    "placement-request-unrelated-correlation.json": "schema",
    "public-sdk-provider-authority.json": "schema"
  }
}
```

| Field | Meaning |
| --- | --- |
| `contract` | Contract name and version the directory belongs to. |
| `description` | Fixed provenance and semantics text. |
| `layers` | Every fixture filename in the directory mapped to its rejecting layer. Sorted; exhaustive. |

| Layer value | Meaning |
| --- | --- |
| `"schema"` | The canonical JSON Schema alone rejects the document. Any conformant reader rejects it, including a third-party validator with no Mosaic code. |
| `"semantic"` | The schema **accepts** the document; a semantic validator rule rejects it. A reader that only validates against the schema will wrongly accept it. |

`rejection-layers.json` is metadata, not a fixture. Fixture-discovery code
excludes it by name.

### Generating and checking

```sh
npm --prefix protocol run generate:rejection-layers   # rewrite all metadata
npm --prefix protocol run validate                    # reconcile against reality
```

The classification is **derived by running every fixture against the pure schema
with no semantic validator attached** — never hand-written. `validate` re-runs
the probe and fails if committed metadata disagrees, naming the fixture and both
layers. A schema change that moves a fixture between layers therefore cannot be
committed without the metadata diff showing it.

Adding a new `invalid/` directory without registering it in
`protocol/tools/generate-rejection-layers.mjs` also fails validation, so a new
contract cannot ship unclassified fixtures.

### Reading it

A `"semantic"` fixture is a standing note that the canonical schema is more
permissive than the contract. That is often legitimate — no JSON Schema can
verify a SHA-256 digest. But a `"semantic"` entry for a rule JSON Schema *could*
express is a divergence defect: see
[breaking-change-process.md](breaking-change-process.md#divergence-is-itself-a-defect).
